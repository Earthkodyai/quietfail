# บทคัดย่อ

การค้นหาแบบเวกเตอร์ (vector search) ถูกนำมาใช้อย่างแพร่หลายในระบบสารสนเทศปัจจุบัน
ทั้งในระบบถามตอบที่ดึงข้อมูลจากเอกสาร (retrieval-augmented generation) ระบบแนะนำ
และการค้นหาเชิงความหมาย ระบบเหล่านี้อาศัยดัชนีแบบประมาณ (approximate nearest
neighbor index หรือ ANN index) เพื่อให้ค้นหาได้เร็วพอใช้งานจริง ซึ่งแลกมาด้วยความถูกต้อง
ที่ลดลง ปัญหาสำคัญคือความถูกต้องที่ลดลงนี้**ไม่ปรากฏเป็นข้อผิดพลาดใด ๆ** ระบบยังคืน
ผลลัพธ์ที่มีรูปแบบสมบูรณ์ทุกประการ ผู้พัฒนาจึงไม่มีทางทราบว่าคำตอบที่ควรได้หายไปแล้ว

งานวิจัยนี้ประยุกต์ระเบียบวิธี **fault injection** เพื่อวัดขนาดของความล้มเหลวเงียบดังกล่าว
บนระบบ PostgreSQL 17.10 ร่วมกับส่วนขยาย pgvector 0.8.5 โดยจงใจสร้างความผิดพลาด
ที่พบได้จริงในการใช้งานจำนวน 12 รูปแบบ แล้ววัดผลเทียบกับเฉลยที่ได้จากการค้นแบบสมบูรณ์
(exact search) ซึ่งเป็นคำตอบที่ถูกต้องตามนิยาม

ผลการทดลองบนข้อมูลสังเคราะห์ 100,000 และ 500,000 รายการ พบว่าที่ค่าตั้งต้นของระบบ
ดัชนีแบบ HNSW ทำให้การค้นหาเร็วขึ้น 117 เท่า แต่คืนคำตอบถูกต้องครบ 10 อันดับแรก
เพียง **2 จาก 200 คำถาม** และทุกรูปแบบการตั้งค่าที่ทดสอบมีคำถามที่ได้คำตอบถูกต้อง
**ศูนย์รายการ** งานวิจัยยังพบว่าความผิดพลาด 11 จาก 12 รูปแบบสามารถตรวจจับล่วงหน้า
ด้วยโปรแกรมอัตโนมัติได้ โดย 5 รูปแบบตรวจได้จากข้อมูลระบบของฐานข้อมูลเพียงอย่างเดียว
ไม่ต้องใช้ข้อมูลจริงและไม่ต้องรอให้ปัญหาเกิดขึ้นก่อน

นอกจากนี้ยังพบว่าเอกสารทางการของ pgvector ให้ข้อมูลที่ไม่ถูกต้องหรือไม่ครบถ้วน 3 จุด
ซึ่งตรวจพบจากการวัดทั้งหมด และการทดสอบโค้ดที่สร้างโดยปัญญาประดิษฐ์พบว่าติดกับดัก
5 จาก 10 โจทย์ โดยกรณีที่สำคัญที่สุดคือแบบจำลองอธิบายกลไกของปัญหาได้ถูกต้องและ
ตั้งค่าตามเอกสารครบทุกตัว แต่ยังคืนผลลัพธ์ศูนย์รายการ เนื่องจากพารามิเตอร์ที่แก้ปัญหา
ได้จริงไม่ปรากฏในเอกสาร

ผลผลิตของงานวิจัยประกอบด้วยชุดทดลองที่ทำซ้ำได้ เครื่องมือตรวจจับที่ใช้กับฐานข้อมูลอื่นได้
และรายงานผลพร้อมข้อจำกัด

**คำสำคัญ:** ความล้มเหลวเงียบ, การค้นหาแบบเวกเตอร์, การฉีดความผิดพลาด, ค่าเรียกคืน,
ฐานข้อมูลเชิงสัมพันธ์, การประกันคุณภาพซอฟต์แวร์

# ABSTRACT

Vector search underpins a growing share of modern information systems, including
retrieval-augmented generation, recommendation, and semantic search. These systems
rely on approximate nearest neighbor (ANN) indexes to achieve practical query
latency, trading correctness for speed. The critical problem is that this loss of
correctness **raises no error**. The system returns a structurally complete result
set, so developers have no signal that answers are missing.

This research applies **fault injection** to measure the magnitude of such silent
failures on PostgreSQL 17.10 with the pgvector 0.8.5 extension. Twelve realistic
misconfigurations were deliberately introduced and measured against ground truth
obtained from exact search, which is correct by definition.

On synthetic datasets of 100,000 and 500,000 records, an HNSW index at default
settings was 117 times faster while returning a fully correct top-10 for only
**2 of 200 queries**. Every configuration tested contained queries returning **zero**
correct results. Eleven of the twelve fault types proved automatically detectable in
advance; five require only database catalog inspection, needing neither production
data nor a prior incident.

The work additionally identified three points where the official pgvector
documentation is incorrect or incomplete, all found through measurement. Testing of
AI-generated code found traps in 5 of 10 tasks; most notably, the model correctly
described the failure mechanism and applied every documented remedy, yet still
returned zero rows, because the parameter that actually resolves the problem is
absent from the documentation.

Deliverables comprise a reproducible test harness, a portable detection tool, and a
results report with stated limitations.

**Keywords:** silent failure, vector search, fault injection, recall, relational
database, software quality assurance

# บทที่ 1 คำนำ

## 1.1 ความสำคัญของปัญหา

ระบบสารสนเทศจำนวนมากในปัจจุบันนำการค้นหาแบบเวกเตอร์มาใช้เป็นองค์ประกอบหลัก
กลไกการทำงานคือการแปลงข้อมูลแต่ละรายการเป็นเวกเตอร์ตัวเลขที่สะท้อนความหมาย
(embedding) แล้วค้นหาโดยวัดระยะห่างระหว่างเวกเตอร์ รายการที่มีความหมายใกล้เคียงกัน
จะมีเวกเตอร์อยู่ใกล้กันในปริภูมิหลายมิติ

เมื่อข้อมูลมีจำนวนมาก การเปรียบเทียบกับทุกรายการมีต้นทุนสูงเกินกว่าจะใช้งานได้จริง
แนวทางมาตรฐานจึงใช้ดัชนีแบบ ANN ซึ่งลดจำนวนรายการที่ต้องเปรียบเทียบลง
โดยยอมรับว่าผลลัพธ์อาจไม่ครบถ้วน

ประเด็นที่งานวิจัยนี้ให้ความสำคัญคือ **ลักษณะของความล้มเหลว** ไม่ใช่ตัวความล้มเหลวเอง

ฐานข้อมูลเชิงสัมพันธ์แบบดั้งเดิมเมื่อมีการใช้งานผิดพลาด มักแสดงข้อผิดพลาดออกมา
หรือให้ผลลัพธ์ที่ผิดในลักษณะที่สังเกตเห็นได้ แต่การค้นหาแบบเวกเตอร์ที่ตั้งค่าไม่เหมาะสม
จะคืนผลลัพธ์ที่มีจำนวนแถวสมเหตุสมผล มีโครงสร้างถูกต้อง และเรียงลำดับอย่างเป็นระบบ
ต่างกันเพียงว่ารายการที่ควรปรากฏบางส่วนหายไป

ผู้พัฒนาจึงไม่ได้รับสัญญาณเตือนใด ๆ ระบบเฝ้าระวังไม่แจ้งเหตุ และปัญหามักถูกค้นพบ
เมื่อผู้ใช้ปลายทางรายงานว่าค้นหาไม่พบสิ่งที่ควรพบ ซึ่งเป็นเวลาที่สายเกินกว่าจะแก้ไข
ได้โดยไม่กระทบผู้ใช้

เอกสารทางการของ pgvector ระบุไว้เองว่าการเพิ่มดัชนีแบบประมาณ *เปลี่ยนผลลัพธ์ของ
คำสั่งค้นหา* ไม่ใช่เพียงทำให้เร็วขึ้น งานวิจัยนี้จึงไม่ได้มุ่งค้นพบว่าปัญหามีอยู่จริงหรือไม่
แต่มุ่ง **วัดขนาดของปัญหา** และ **สร้างวิธีตรวจจับล่วงหน้า** ซึ่งเป็นสิ่งที่ยังไม่ปรากฏ
ในงานที่มีอยู่

## 1.2 วัตถุประสงค์ของการวิจัย

1. เพื่อวัดปริมาณผลลัพธ์ที่สูญหายจากการตั้งค่าดัชนี ANN ที่ไม่เหมาะสม โดยไม่มีการแจ้ง
   ข้อผิดพลาด เปรียบเทียบกับผลจากการค้นแบบสมบูรณ์
2. เพื่อพัฒนาและประเมินวิธีตรวจจับความผิดพลาดดังกล่าวโดยอัตโนมัติ พร้อมระบุว่า
   แต่ละวิธีอาศัยหลักฐานประเภทใด
3. เพื่อศึกษาอัตราการเกิดความผิดพลาดเหล่านี้ในโค้ดที่สร้างโดยปัญญาประดิษฐ์

## 1.4 ขอบเขตของการวิจัย

**สิ่งที่ศึกษา**

- ระบบ PostgreSQL รุ่น 17.10 ร่วมกับ pgvector รุ่น 0.8.5 ระบุรุ่นแบบเจาะจงในทุกผลการทดลอง
- ดัชนี 2 ชนิด คือ HNSW และ IVFFlat โดยการเปรียบเทียบระหว่างสองชนิดเป็นส่วนหนึ่งของผล
- ความผิดพลาด 12 รูปแบบ ครอบคลุมช่วงติดตั้ง ช่วงเรียกใช้ และช่วงใช้งานระยะยาว
- ข้อมูลสังเคราะห์ที่ควบคุมการกระจายตัวได้ เพื่อให้ทราบเฉลยอย่างแน่นอน

**สิ่งที่ไม่ศึกษา**

| ไม่ศึกษา | เหตุผล |
|---|---|
| การวัดค่าเรียกคืนอย่างละเอียดกับทุกระบบค้นหาเวกเตอร์ | ต้นทุนเกินขอบเขต ใช้การทบทวนเอกสารแทนในระดับที่สาม |
| ระบบที่เป็นบริการเชิงพาณิชย์แบบปิด | ความผิดพลาดช่วงติดตั้งหายไปทั้งหมดเพราะผู้ให้บริการจัดการดัชนีให้ และทำซ้ำไม่ได้ |
| การเปรียบเทียบแบบจำลองสร้าง embedding หลายตัว | เป็นคำถามวิจัยคนละประเด็น |
| ข้อมูลจากระบบใช้งานจริง | ไม่สามารถทราบเฉลยที่ถูกต้องได้ ซึ่งเป็นข้อบังคับของระเบียบวิธี |

## 1.5 ประโยชน์ที่คาดว่าจะได้รับ

2. เครื่องมือตรวจจับที่ทีมพัฒนานำไปใช้กับฐานข้อมูลของตนได้ทันที
3. ชุดทดลองที่ทำซ้ำได้ สำหรับใช้เป็นฐานในการศึกษาต่อ

# บทที่ 2 การตรวจเอกสาร

## 2.1 การค้นหาเพื่อนบ้านใกล้ที่สุดแบบประมาณ

ปัญหาการค้นหาเพื่อนบ้านใกล้ที่สุด (nearest neighbor search) คือการหารายการ k รายการ
ที่มีระยะห่างจากจุดคำถามน้อยที่สุด การแก้ปัญหาแบบสมบูรณ์ต้องคำนวณระยะห่างกับทุกรายการ
ซึ่งมีความซับซ้อนเชิงเส้นตามจำนวนข้อมูล

ในปริภูมิมิติสูง โครงสร้างข้อมูลแบบแบ่งปริภูมิดั้งเดิมสูญเสียประสิทธิภาพ จึงเกิดแนวทาง
**การค้นหาแบบประมาณ** ซึ่งยอมรับว่าผลลัพธ์อาจไม่ใช่เพื่อนบ้านที่ใกล้ที่สุดจริง
เพื่อแลกกับความเร็วที่เพิ่มขึ้นหลายสิบถึงหลายร้อยเท่า

ตัวชี้วัดคุณภาพมาตรฐานคือ **ค่าเรียกคืน (recall@k)** นิยามเป็นสัดส่วนของรายการที่ถูกต้อง
ซึ่งปรากฏในผลลัพธ์ k อันดับแรก เทียบกับผลจากการค้นแบบสมบูรณ์

## 2.2 ดัชนีที่ศึกษาในงานวิจัยนี้

### 2.2.1 HNSW

Hierarchical Navigable Small World สร้างกราฟหลายชั้นที่เชื่อมโยงรายการที่อยู่ใกล้กัน
การค้นหาเริ่มจากชั้นบนซึ่งเชื่อมโยงแบบกระโดดไกล แล้วไล่ลงชั้นล่างที่ละเอียดขึ้น

พารามิเตอร์สำคัญขณะค้นหาคือ `hnsw.ef_search` ซึ่งกำหนดขนาดรายการผู้เข้ารอบ
ที่ระบบเก็บไว้ระหว่างการเดินกราฟ ค่าตั้งต้นใน pgvector 0.8.5 คือ **40**

### 2.2.2 IVFFlat

Inverted File with Flat compression แบ่งข้อมูลออกเป็นกลุ่มด้วยขั้นตอนวิธี k-means
ขณะสร้างดัชนี การค้นหาจะเปรียบเทียบเฉพาะกลุ่มที่มีจุดศูนย์กลางใกล้คำถามที่สุด

พารามิเตอร์สำคัญคือ `lists` (จำนวนกลุ่ม) ขณะสร้าง และ `ivfflat.probes` (จำนวนกลุ่ม
ที่เปิดค้น) ขณะค้นหา ค่าตั้งต้นของ `probes` คือ **1** ขณะที่เอกสารแนะนำ `sqrt(lists)`

### 2.2.3 ข้อสังเกตเชิงโครงสร้างของค่าตั้งต้น

`ef_search` เป็นค่าสัมบูรณ์ที่ไม่เปลี่ยนตามขนาดข้อมูล ขณะที่ `probes` เป็นค่าสัมพัทธ์
กับจำนวนกลุ่ม ความแตกต่างนี้ทำให้ดัชนีสองชนิดเสื่อมคุณภาพตามขนาดข้อมูลในลักษณะ
ที่ต่างกัน ซึ่งเป็นประเด็นที่ผลการทดลองในบทที่ 4 ยืนยัน

## 2.3 ข้อจำกัดที่เอกสารทางการระบุไว้

การทบทวนเอกสารของ pgvector รุ่น 0.8.5 พบข้อกำหนดที่เกี่ยวข้องโดยตรง ดังนี้

1. รูปแบบคำสั่งค้นหาต้องมี `ORDER BY` ตามด้วย distance operator โดยตรง และมี `LIMIT`
   จึงจะใช้ดัชนีได้ การห่อ operator ด้วยนิพจน์ใด ๆ ทำให้ดัชนีถูกข้าม
2. ต้องสร้างดัชนีแยกต่างหากสำหรับแต่ละฟังก์ชันระยะทาง โดยใช้ operator class ที่ตรงกัน
3. การกรองด้วยเงื่อนไข `WHERE` ทำงาน **หลัง** ดัชนีคืนรายการผู้เข้ารอบแล้ว
4. เวกเตอร์ที่เป็นค่าว่างไม่ถูกบรรจุในดัชนี และเวกเตอร์ศูนย์ไม่ถูกบรรจุเมื่อใช้ระยะทางแบบ cosine
5. แถวที่ถูกลบแล้วแต่ยังไม่ถูกเก็บกวาดอาจทำให้ผลลัพธ์ที่ได้น้อยลง
6. โหมดค้นต่อเนื่อง (iterative scan) มีตั้งแต่รุ่น 0.8.0 แต่ยังปิดเป็นค่าตั้งต้น

ข้อกำหนดเหล่านี้ถูกใช้เป็นฐานในการออกแบบความผิดพลาดที่จะฉีดในบทที่ 3


การระบุรุ่นของคอนเทนเนอร์แบบเจาะจงเป็นข้อกำหนดของงานวิจัยนี้ เนื่องจากป้ายรุ่นแบบย่อ
จะเลื่อนไปยังรุ่นใหม่เมื่อมีการเผยแพร่ ทำให้ผลการทดลองเปรียบเทียบกันไม่ได้
โดยไม่มีสัญญาณเตือน

ใช้การตั้งค่าสองชุด ชุดหนึ่งกำหนดค่าทรัพยากรต่ำเพื่อให้ความผิดพลาดแสดงตัวเร็ว
และอีกชุดใช้ค่าที่ใกล้เคียงระบบใช้งานจริงเป็นกลุ่มเปรียบเทียบ

## 3.2 ข้อมูลที่ใช้ทดลอง

### 3.2.1 ลักษณะและที่มา

ข้อมูลเป็นเวกเตอร์สังเคราะห์ขนาด 384 มิติ จัดกลุ่มตามความหมายเป็น 50 กลุ่ม
สร้างด้วยสูตรที่กำหนดผลลัพธ์ได้แน่นอน (deterministic) โดยคำนวณจากค่าแฮชของคีย์
ไม่ใช้ฟังก์ชันสุ่มที่ขึ้นกับลำดับการเรียก จึงสร้างซ้ำได้ผลเดิมทุกครั้ง

| รายการ | ค่า |
|---|---|
| ขนาดข้อมูล | 100,000 และ 500,000 รายการ |
| มิติ | 384 |
| จำนวนกลุ่ม | 50 |
| ชุดคำถามทดสอบ | 200 คำถาม ครอบคลุมครบทุกกลุ่ม |
| ฟังก์ชันระยะทาง | cosine |

### 3.2.2 เหตุผลที่ใช้ข้อมูลสังเคราะห์

ระเบียบวิธีของงานนี้ต้องการ **เฉลยที่ถูกต้องแน่นอน** เพื่อใช้เป็นฐานเปรียบเทียบ
ข้อมูลจากระบบใช้งานจริงไม่สามารถให้เฉลยเช่นนี้ได้ เนื่องจากไม่มีผู้ใดทราบว่าคำตอบ
ที่ถูกต้องคืออะไร การใช้ข้อมูลสังเคราะห์จึงเป็นข้อบังคับของระเบียบวิธี ไม่ใช่การลดทอน

### 3.2.3 การตรวจสอบความสมเหตุสมผลของข้อมูล

ก่อนใช้ข้อมูลชุดใดวัดผล ต้องผ่านการตรวจสองประการ

1. **ค่าลายนิ้วมือ (fingerprint)** ของทั้งชุดข้อมูลและชุดคำถาม ต้องตรงกับค่าที่บันทึกไว้
   เพื่อยืนยันว่าไม่มีการแก้ไขภายหลัง
2. **ระยะห่างภายในกลุ่มกับข้ามกลุ่มต้องแยกจากกันชัดเจน** วัดได้ 0.3820 และ 0.9997
   ตามลำดับ (ห่างกัน 2.6 เท่า) หากสองค่านี้ใกล้กัน แปลว่าข้อมูลไม่มีโครงสร้างเชิงกลุ่มจริง
   และค่าเรียกคืนที่วัดได้จะไม่มีความหมาย

การตรวจข้อที่สองมีที่มาจากความผิดพลาดที่เกิดขึ้นจริงระหว่างพัฒนา ซึ่งบันทึกไว้ในบทที่ 4

## 3.3 การกำหนดเฉลย

เฉลยของงานวิจัยนี้มาจากสองกลไกที่ทำงานร่วมกัน

**กลไกที่ 1 การฉีดความผิดพลาด** ผู้วิจัยเป็นผู้สร้างความผิดพลาดขึ้นเอง จึงทราบสาเหตุ
อย่างแน่นอน ไม่ต้องอนุมานจากอาการ ทุกความผิดพลาดมีเงื่อนไขตรวจสอบ (assertion) กำกับ
หากฉีดแล้วไม่เกิดผลตามที่ออกแบบ สคริปต์จะยุติด้วยข้อผิดพลาด ไม่อนุญาตให้บันทึกผล

**กลไกที่ 2 การค้นแบบสมบูรณ์เป็นเฉลยของค่าเรียกคืน** ใช้วิธีที่เอกสารทางการแนะนำ

```sql
BEGIN;
SET LOCAL enable_indexscan = off;
SELECT ... ORDER BY embedding <=> $1 LIMIT $2;
COMMIT;
```

วิธีนี้บังคับให้ระบบเปรียบเทียบทุกรายการ ผลที่ได้จึงถูกต้องตามนิยาม และไม่เปลี่ยนแปลง
สภาพฐานข้อมูล ต่างจากการลบดัชนีทิ้งซึ่งกระทบการทดลองอื่น

## 3.4 การเลือกค่า k ในการวัด

งานวิจัยนี้ใช้ recall@10 เป็นตัวชี้วัดหลัก เนื่องจากเป็นหน่วยเดียวกับที่ระบบจริง
ส่งมอบผลลัพธ์ กล่าวคือ ระบบถามตอบที่ดึงข้อมูลจากเอกสารมักใช้เอกสารประกอบ 5 ถึง 10 ชิ้น
ต่อหนึ่งคำถาม หน้าแสดงผลการค้นหาและระบบแนะนำแสดงประมาณ 10 รายการแรก และผู้ใช้
มักไม่ดูเกินหน้าแรก การวัดที่ 10 อันดับแรกจึงสะท้อนสิ่งที่ถึงมือผู้ใช้จริง

มีการวัดที่ 100 อันดับควบคู่ เพื่อสังเกตพฤติกรรมเมื่อขอผลลัพธ์จำนวนมากขึ้น

## 3.6 กระบวนการทำงานต่อหนึ่งความผิดพลาด

1. เขียนนิยามให้ครบ 5 ส่วน ได้แก่ อาการ สาเหตุ วิธีฉีด เฉลย และเงื่อนไขตรวจสอบ
2. เขียนโปรแกรมฉีดความผิดพลาด
3. เขียนไฟล์เฉลยพร้อมข้อมูลรุ่นและวันที่
4. เพิ่มตัวตรวจจับ
5. รันติดต่อกัน 3 รอบ และบันทึกผลดิบ
6. **พิสูจน์ว่าตัวตรวจจับจำแนกสถานะได้จริง** ต้องแสดงได้ทั้งกรณีพบและไม่พบ
7. ตรวจความสอดคล้องทั้งโครงการด้วยโปรแกรมอัตโนมัติ

ขั้นตอนที่ 6 เป็นข้อกำหนดที่แยกจากขั้นตอนที่ 5 อย่างชัดเจน เนื่องจากเงื่อนไขตรวจสอบ
ตอบคำถามว่า *ความผิดพลาดเกิดขึ้นจริงหรือไม่* ขณะที่ขั้นตอนที่ 6 ตอบคำถามว่า
*ตัวตรวจจับใช้การได้หรือไม่* ตัวตรวจจับที่ตอบว่าพบปัญหาเสมอไม่ว่าสภาพใด
ไม่ได้วัดสิ่งใดเลย

## 3.7 การออกแบบตัวตรวจจับ

ตัวตรวจจับให้ผลลัพธ์ **3 สถานะ** ไม่ใช่ 2 สถานะ

| สถานะ | ความหมาย |
|---|---|
| `DETECTED` | ตรวจแล้วพบปัญหา |
| `NOT_DETECTED` | ตรวจแล้วไม่พบปัญหา |
| `CANNOT_CHECK` | **ตรวจไม่ได้** เช่น ไม่มีดัชนีให้ตรวจ หรือไม่มีข้อมูลที่จำเป็น |

การแยกสถานะที่สามออกมาเป็นหลักการสำคัญของงานนี้ เครื่องมือที่รายงานว่าระบบปลอดภัย
ทั้งที่ไม่ได้ตรวจสิ่งใดเลย มีอันตรายมากกว่าการไม่มีเครื่องมือ เพราะสร้างความเชื่อมั่นที่ผิด

ตัวอย่างที่ตัวตรวจจับปฏิเสธการให้คำตอบ

- ตัวตรวจของ Q03 และ L02 ปฏิเสธเมื่อจำนวนผลลัพธ์ที่ขอไม่ต่ำกว่า `ef_search`
  เนื่องจากจะแยกจากความผิดพลาด Q06 ไม่ได้
- ตัวตรวจของ I04 ปฏิเสธเมื่อไม่มีบันทึกว่าค่าเรียกคืนถูกวัดบนดัชนีรุ่นใด
- ตัวตรวจของ I05 ปฏิเสธเมื่อมิติของข้อมูลต่างจากที่ปรับเทียบค่าไว้

## 3.8 การควบคุมคุณภาพของกระบวนการ

**การรันซ้ำ** ทุกการวัดรันติดต่อกัน 3 รอบ ส่วนที่เกี่ยวกับการสร้างดัชนีซึ่งพิสูจน์แล้วว่า
ไม่ให้ผลเหมือนเดิม ต้องสร้างซ้ำ 5 รอบต่อหนึ่งการตั้งค่า และรายงานเป็นช่วงค่า
พร้อมผลรายคำถาม ไม่ใช่เพียงค่าเฉลี่ย

**ตัวชี้วัดด้านทรัพยากร** ใช้จำนวนบล็อกที่อ่าน (buffers) เป็นหลัก แทนการใช้เวลา
เนื่องจากเวลาแปรผันตามฮาร์ดแวร์ได้หลายเท่า ขณะที่จำนวนบล็อกเป็นค่าเชิงโครงสร้าง

**การตรวจสอบทั้งโครงการ** มีโปรแกรมตรวจความสอดคล้อง 25 หัวข้อ ครอบคลุมความครบถ้วน
ของหลักฐาน ความตรงกันระหว่างเอกสาร สภาพฐานข้อมูล และความสามารถในการทำงาน
ของตัวนับคะแนน ใช้เวลาประมาณ 30 วินาที

## 3.9 การทดสอบโค้ดที่สร้างโดยปัญญาประดิษฐ์

สร้างชุดโจทย์ 10 ข้อที่มีลักษณะเหมือนงานจริง โดยไม่มีคำใบ้เกี่ยวกับดัชนีหรือการปรับแต่ง
แต่ละโจทย์ถามในบทสนทนาแยกกัน ใช้คำตอบแรกโดยไม่ถามซ้ำ

การให้คะแนนใช้วิธี **นำคำสั่งที่ได้ไปรันจริงบนฐานข้อมูล** แล้ววัดผลเทียบกับการค้นแบบสมบูรณ์
ไม่ใช่การตรวจรูปแบบของคำสั่ง เนื่องจากคำสั่งที่มีรูปแบบถูกต้องทุกประการยังคืนผลลัพธ์
ไม่ครบได้ ดังที่ความผิดพลาด Q03 แสดงไว้

## 4.3 เอกสารทางการไม่ถูกต้องหรือไม่ครบถ้วน

ผลส่วนนี้ไม่ได้อยู่ในวัตถุประสงค์เดิม แต่ปรากฏขึ้นจากการวัดตามกระบวนการปกติ

### 4.3.1 ค่าที่เอกสารแนะนำสูงเกินความจำเป็น

**ตารางที่ 4** ผลของ `ivfflat.probes` ที่ `lists` = 100

| `probes` | สถานะ | recall@10 | ครบ 10/10 | เวลา 200 คำถาม |
|---|---|---|---|---|
| 1 | ค่าตั้งต้น | 0.7370 | 78/200 | 277 ms |
| **5** | | **1.0000** | **200/200** | 495 ms |
| 10 | เอกสารแนะนำ | 1.0000 | 200/200 | 1,101 ms |

ค่า `probes` = 5 ให้ค่าเรียกคืนสมบูรณ์แล้ว ขณะที่ค่า 10 ตามที่เอกสารแนะนำ
ใช้เวลามากกว่า 2.2 เท่าโดยไม่ได้ค่าเรียกคืนเพิ่มขึ้น

ข้อค้นพบนี้แสดงว่า **ทั้งค่าตั้งต้นที่ผู้พัฒนากำหนดและสูตรที่ผู้พัฒนาแนะนำ
ต่างก็ไม่ใช่คำตอบที่เหมาะสมสำหรับข้อมูลชุดนี้** ค่าที่เหมาะสมได้จากการวัดเท่านั้น

### 4.3.2 คำเตือนของระบบปรากฏในกรณีที่ไม่จำเป็น และเงียบในกรณีที่ควรเตือน

**ตารางที่ 5** ผลของช่วงเวลาที่สร้างดัชนี โดยข้อมูลปลายทางเหมือนกันทุกประการ

| เงื่อนไข | สร้างดัชนีเมื่อมี | กลุ่มที่ปรากฏขณะสร้าง | ระบบเตือน | recall@10 |
|---|---|---|---|---|
| ก | 50 รายการ | 50 จาก 50 | **มี** | **1.0000** |
| ข | 1,000 รายการ | 50 จาก 50 | ไม่มี | 0.8798 |
| ค | 100,000 รายการ | 50 จาก 50 | ไม่มี | 0.7682 |
| **ง** | 1,000 รายการ | **5 จาก 50** | **ไม่มี** | **0.2278** |

คำเตือนของระบบปรากฏเฉพาะเมื่อจำนวนแถวน้อยกว่าจำนวนกลุ่มที่กำหนด ซึ่งเป็นกรณี
ที่ได้ค่าเรียกคืนสมบูรณ์ ขณะที่เงื่อนไข ง ซึ่งสูญเสียผลลัพธ์ถึง 77 เปอร์เซ็นต์
กลับไม่มีคำเตือนใด ๆ นอกจากนี้ข้อความในคำเตือนระบุว่าจะทำให้ค่าเรียกคืนต่ำ
ซึ่งการวัดพิสูจน์แล้วว่าไม่เป็นความจริงกับข้อมูลชุดนี้

**ตัวแปรที่แท้จริงคือความเป็นตัวแทนของข้อมูล ไม่ใช่จำนวนแถว** ข้อมูล 50 รายการ
ที่ครอบคลุมครบ 50 กลุ่ม ให้ผลดีกว่าข้อมูล 1,000 รายการจากเพียง 5 กลุ่มถึง 20 เท่า

### 4.3.3 วิธีแก้ปัญหาที่เอกสารระบุ ไม่ทำงานจนกว่าจะปรับค่าที่เอกสารไม่ได้กล่าวถึง

**ตารางที่ 6** ผลของการปรับพารามิเตอร์ทีละตัว ที่เงื่อนไขกรองตรง 1 เปอร์เซ็นต์ ขอ 40 รายการ

| การปรับ | ได้ผลลัพธ์ | บล็อกที่อ่าน |
|---|---|---|
| ค่าตั้งต้นทั้งหมด | 0 | 977 |
| เปิด `hnsw.iterative_scan` | **0** | 1,743 |
| เพิ่ม `max_scan_tuples` 10 เท่า | **0** | 1,743 |
| เพิ่ม `scan_mem_multiplier` 8 เท่า | **0** | 3,035 |
| **เพิ่ม `work_mem` จาก 64kB เป็น 4MB** | **40** | 27,145 |

พารามิเตอร์ที่เกี่ยวข้องกับ pgvector ทุกตัวไม่ทำให้ผลลัพธ์เปลี่ยนแปลง ค่าที่แก้ปัญหา
ได้จริงคือ `work_mem` ซึ่งเป็นค่าทั่วไปของ PostgreSQL ที่ไม่เกี่ยวข้องกับการค้นหา
แบบเวกเตอร์โดยตรง และไม่ปรากฏในรายการข้อจำกัดที่เอกสารระบุไว้

ที่สำคัญกว่านั้น การปรับสามขั้นแรกทำให้ระบบอ่านข้อมูลเพิ่มขึ้นจริง โดยไม่ได้ผลลัพธ์
เพิ่มขึ้นแม้แต่รายการเดียว ผู้ที่ปรับแต่งตามเอกสารครบทุกข้อจึงพบว่าระบบทำงานช้าลง
ในขณะที่ผลลัพธ์ยังเป็นศูนย์ และอาจสรุปว่าโหมดค้นต่อเนื่องใช้งานไม่ได้

|---|---|---|---|
| Q06 | k = `ef_search` + 1 | ขอ 40 ได้ 40 | ขอ 41 ได้ **40** |
| Q03 | เงื่อนไขกรองตรง 20% ลงมาถึง 2% | ขอ 10 ได้ 10 | ขอ 10 ได้ **0** |
| L02 | แถวที่ถูกลบ 40% ถึง 50% | ขอ 10 ได้ 10 | ขอ 10 ได้ **0** |

ความผิดพลาดทั้งสามรูปแบบเปลี่ยนจากสภาพปกติเป็นสภาพที่ไม่คืนผลลัพธ์เลยภายในระยะ
ที่แคบมาก ไม่ได้ค่อย ๆ เสื่อมลง ข้อค้นพบนี้มีนัยสำคัญต่อการออกแบบระบบเฝ้าระวัง
เนื่องจากระบบที่ทำงานแบบกำหนดค่าขีดแบ่งไม่สามารถจับความล้มเหลวลักษณะนี้ได้ทัน

**Q03 และ L02 มีกลไกเดียวกันทุกประการ** ต่างกันที่ตัวกรอง ในกรณี Q03 ตัวกรองคือ
เงื่อนไข `WHERE` ที่ผู้พัฒนาเขียนเอง จึงมองเห็นได้จากโค้ด ส่วน L02 ตัวกรองคือกลไก
ควบคุมความสอดคล้องของข้อมูล (MVCC) ที่คัดแถวซึ่งถูกลบแล้วออก **ซึ่งไม่ปรากฏ
ในคำสั่งใด ๆ เลย** คำสั่งที่ให้ผลลัพธ์ผิดจึงมีหน้าตาเหมือนคำสั่งที่ถูกต้องทุกตัวอักษร

## 4.5 ผลตอบคำถามการวิจัยข้อที่ 3

**ตารางที่ 8** สรุปผลการทดสอบโค้ดที่สร้างโดยปัญญาประดิษฐ์

### 4.5.1 กรณีที่มีนัยสำคัญที่สุด

ในโจทย์ที่ระบุเงื่อนไขไว้อย่างชัดเจนว่าต้องได้ผลลัพธ์ครบทุกครั้งไม่ว่าจะกรองด้วยเงื่อนไขใด
แบบจำลองได้เขียนคำอธิบายกลไกของปัญหาไว้ในหมายเหตุของคำตอบเองอย่างถูกต้อง ว่าดัชนี
คืนรายการผู้เข้ารอบตามจำนวนที่กำหนดก่อน แล้วจึงกรองภายหลัง ทำให้หมวดที่มีข้อมูลน้อย
ได้ผลลัพธ์ไม่ครบ

จากนั้นได้ตั้งค่าพารามิเตอร์ครบทุกตัวที่เอกสารของ pgvector ระบุไว้ ผลที่ได้คือ
**ศูนย์รายการ** และเมื่อเพิ่มเฉพาะค่า `work_mem` โดยไม่แก้ไขสิ่งอื่นใด ผลลัพธ์กลับมา
ครบถ้วน

ข้อค้นพบนี้แสดงว่าสาเหตุไม่ได้อยู่ที่แบบจำลองไม่รู้จักปัญหา เนื่องจากแบบจำลอง
วินิจฉัยกลไกได้ถูกต้อง แต่อยู่ที่ **ความรู้ซึ่งแบบจำลองเรียนมาจากเอกสาร ขาดในจุด
เดียวกับที่เอกสารขาด** ผลข้อนี้จึงยืนยันข้อค้นพบในหัวข้อ 4.3.3 ด้วยหลักฐานคนละประเภท

### 4.5.2 กรณีที่แบบจำลองทำนายพฤติกรรมของตัวเลือกแผนผิด

ในอีกโจทย์หนึ่ง แบบจำลองระบุในหมายเหตุว่าเมื่อข้อมูลในหมวดมีน้อย ระบบจะเลือกใช้
การค้นแบบสมบูรณ์และให้ผลครบถ้วน จึงสร้างดัชนีแบบ B-tree บนคอลัมน์ที่ใช้กรอง

การวัดจริงพบว่าตัวเลือกแผนไม่ได้เลือกเช่นนั้น ยังคงใช้ดัชนีเวกเตอร์และนำเงื่อนไขกรอง
ไปใช้ภายหลัง ผลลัพธ์ที่ได้คือศูนย์รายการ

## 4.6 การวัดหักล้างสมมติฐานของผู้วิจัยเอง

ชื่อและคำอธิบายสาเหตุที่ผู้วิจัยกำหนดไว้ตั้งแต่ขั้นวางแผน **ถูกการวัดหักล้าง 4 จาก 12 รูปแบบ**
และทุกครั้งตรวจพบด้วยกลุ่มควบคุม ไม่ใช่ด้วยผลการวัดหลัก

| รูปแบบ | สมมติฐานเดิม | สิ่งที่กลุ่มควบคุมพบ |
|---|---|---|
| Q02 | การใช้ `WHERE` แทน `ORDER BY` | คำสั่งที่มีทั้ง `WHERE`, `ORDER BY` และ `LIMIT` ใช้ดัชนีได้ปกติ สาเหตุที่แท้จริงคือการขาด `ORDER BY` หรือ `LIMIT` |
| I04 | ความสุ่มของ k-means ใน IVFFlat | HNSW ซึ่งไม่มี k-means ก็ให้ผลไม่คงที่เช่นกัน และการปิดการสร้างแบบขนานไม่ได้แก้ปัญหา |
| I02 | การสร้างดัชนีขณะข้อมูลน้อย | ข้อมูล 50 รายการให้ค่าเรียกคืนสมบูรณ์ ตัวแปรที่แท้จริงคือความเป็นตัวแทน |
| L02 | แถวที่ถูกลบทำให้ดัชนีบวมและค่าเรียกคืนลด | การปรับปรุงแถวทำให้ดัชนีบวมจาก 195 เป็น 202 MB แต่ค่าเรียกคืนไม่ลดลง |

ข้อสังเกตเชิงระเบียบวิธีจากผลส่วนนี้คือ หากวัดเฉพาะสิ่งที่ตั้งใจวัด จะสามารถยืนยัน
สมมติฐานที่ผิดได้อย่างสมบูรณ์ทุกครั้ง การมีกลุ่มควบคุมที่สร้างเงื่อนไขซึ่งควรทำให้เกิด
อาการโดยไม่ให้เกิดอาการ จึงเป็นสิ่งจำเป็น ไม่ใช่ทางเลือก

## 4.7 ความสัมพันธ์ระหว่างความผิดพลาด

ความผิดพลาดที่ศึกษาไม่ได้เป็นอิสระต่อกัน แต่เชื่อมโยงกันในลักษณะที่มีนัยสำคัญ

- ค่า recall@100 ของ Q01 ที่ต่ำมาก อธิบายได้ด้วยกลไกของ Q06 กล่าวคือ 40 หารด้วย 100
  เป็นเพดานสูงสุดที่เป็นไปได้ ไม่ใช่ตัวชี้วัดคุณภาพ
- นิพจน์ที่ใช้แก้ปัญหา Q03 บนระบบรุ่น 17 ขึ้นไป เป็นนิพจน์เดียวกับที่ทำให้ดัชนี
  ใช้งานไม่ได้ในความผิดพลาด Q02
- ผลของ I04 ที่ว่าการสร้างดัชนีใหม่ให้คำตอบไม่เหมือนเดิม เป็นข้อบังคับให้การทดลอง
  ของ I02 ต้องสร้างดัชนี 5 รอบต่อเงื่อนไข มิฉะนั้นจะแยกไม่ออกว่าความแตกต่างเกิดจาก
  เงื่อนไขหรือจากความไม่คงที่ของการสร้าง
- ค่า `probes` = 5 แก้ได้ทั้งความผิดพลาด Q04 และ I04 กล่าวคือ ค่าที่เพียงพอ
  ไม่เพียงยกค่าเรียกคืน แต่ทำให้ผลลัพธ์คงที่ด้วย

# บทที่ 5 สรุปและข้อเสนอแนะ

## 5.1 สรุปผลการวิจัย

งานวิจัยนี้ตอบคำถามการวิจัยทั้งสามข้อได้ครบถ้วน

**คำถามข้อที่ 1** การตั้งค่าดัชนี ANN ตามค่าตั้งต้นทำให้ผลลัพธ์ที่ควรได้สูญหายไป
ระหว่าง 14 ถึง 41 เปอร์เซ็นต์ในระดับค่าเฉลี่ย และทุกการตั้งค่าที่ทดสอบมีคำถาม
ที่ได้คำตอบถูกต้องศูนย์รายการ โดยไม่มีข้อผิดพลาดใดปรากฏ

**คำถามข้อที่ 2** ความผิดพลาด 11 จาก 12 รูปแบบตรวจจับล่วงหน้าได้ด้วยโปรแกรมอัตโนมัติ
โดย 5 รูปแบบตรวจได้จากข้อมูลระบบเพียงอย่างเดียว ซึ่งนำไปใช้ในกระบวนการตรวจสอบ
ก่อนนำโค้ดขึ้นระบบจริงได้ทันที

**คำถามข้อที่ 3** โค้ดที่สร้างโดยแบบจำลองภาษาระดับแนวหน้าติดกับดัก 5 จาก 10 โจทย์
โดยกรณีสำคัญที่สุดแสดงว่าปัญหาไม่ได้เกิดจากการที่แบบจำลองไม่รู้จักกลไก แต่เกิดจาก
ช่องว่างของเอกสารที่แบบจำลองเรียนรู้มา

**ผลที่อยู่นอกวัตถุประสงค์เดิมแต่มีนัยสำคัญ** คือการพบว่าเอกสารทางการของ pgvector
ไม่ถูกต้องหรือไม่ครบถ้วนใน 3 จุด ซึ่งตรวจพบจากการวัดทั้งหมด

## 5.2 ข้อจำกัดของงานวิจัย

1. **ทดลองบนเครื่องเดียวและการตั้งค่าเดียว** ค่าที่เกี่ยวกับเวลาจึงใช้เปรียบเทียบ
   ภายในงานนี้เท่านั้น งานวิจัยลดผลกระทบด้วยการใช้จำนวนบล็อกที่อ่านเป็นตัวชี้วัดหลัก
   ซึ่งเป็นค่าเชิงโครงสร้างที่ไม่ขึ้นกับฮาร์ดแวร์
2. **ข้อมูลเป็นข้อมูลสังเคราะห์** ซึ่งจำเป็นต่อการมีเฉลยที่แน่นอน แต่ผลบางส่วน
   โดยเฉพาะของความผิดพลาด I02 ผูกกับคุณสมบัติเชิงโครงสร้างของข้อมูลชุดนี้โดยตรง
3. **กลไกที่ทำให้การสร้างดัชนี HNSW ใหม่ให้ผลไม่เหมือนเดิมยังไม่ทราบ** งานวิจัย
   ตัดสาเหตุที่เป็นไปได้ออกไปสองประการ คือฝั่งคำสั่งค้นหาและการสร้างแบบขนาน
   แต่ยังไม่พบสาเหตุที่แท้จริง
4. **ผลของคำถามข้อที่ 3 มาจากแบบจำลองเดียว ทดสอบครั้งเดียว** จึงยืนยันได้ว่า
   ปรากฏการณ์เกิดขึ้นจริง แต่ยังไม่สามารถระบุเป็นอัตราของแบบจำลองโดยทั่วไป
5. **ความผิดพลาด 3 รูปแบบตรวจได้เฉพาะขณะเกิดเหตุ** เครื่องมือที่ตรวจครั้งเดียว
   ไม่สามารถจับได้

## 5.3 ความเชื่อถือได้ของเครื่องมือวัด

ระหว่างการพัฒนา พบข้อบกพร่องในเครื่องมือที่ผู้วิจัยสร้างขึ้นเองจำนวน 28 รายการ
ซึ่งบันทึกไว้ทั้งหมด ในจำนวนนี้มี 2 กรณีที่ตัวตรวจจับรายงานว่าไม่พบปัญหา
ทั้งที่ความผิดพลาดเกิดขึ้นอยู่จริง

ทั้งสองกรณีถูกตรวจพบด้วยข้อกำหนดในกระบวนการที่แยกคำถามว่า *ความผิดพลาดเกิดขึ้น
จริงหรือไม่* ออกจากคำถามว่า *ตัวตรวจจับใช้การได้หรือไม่* และบังคับให้พิสูจน์อย่างหลัง
แยกต่างหาก

การบันทึกข้อบกพร่องเหล่านี้ไว้อย่างครบถ้วนเป็นส่วนหนึ่งของการรายงานความเชื่อถือได้
ของเครื่องมือวัด ซึ่งจำเป็นต่อการประเมินน้ำหนักของผลการวิจัย

## 5.4 ข้อเสนอแนะสำหรับการนำไปใช้

1. **ตรวจสอบ operator class ของดัชนีให้ตรงกับ operator ที่โปรแกรมใช้** เป็นการตรวจ
   ที่ทำได้ทันทีจากข้อมูลระบบ และป้องกันความผิดพลาดที่ทำให้ดัชนีไม่ถูกใช้เลย
2. **วัดค่าเรียกคืนกับข้อมูลของตนเองก่อนกำหนดค่าพารามิเตอร์** ไม่ควรใช้ค่าตั้งต้น
   หรือสูตรจากเอกสารโดยไม่ตรวจสอบ
3. **รายงานคุณภาพรายคำถามควบคู่กับค่าเฉลี่ย** เนื่องจากค่าเฉลี่ยปกปิดกรณีที่รุนแรง
4. **วัดค่าเรียกคืนใหม่ทุกครั้งหลังสร้างดัชนีใหม่** เนื่องจากการสร้างดัชนีไม่ให้ผลเหมือนเดิม
5. **แยกสถานะตรวจไม่ได้ออกจากสถานะไม่พบปัญหา** ในเครื่องมือตรวจสอบทุกชนิด

## 5.5 ข้อเสนอแนะสำหรับงานวิจัยต่อไป

1. **ขยายการทดสอบคำถามข้อที่ 3 ไปยังแบบจำลองอื่น** เพื่อแยกว่าเป็นลักษณะร่วม
   ของแบบจำลองภาษาโดยทั่วไป หรือเป็นลักษณะเฉพาะของแบบจำลองที่ทดสอบ
   ชุดโจทย์และเครื่องมือให้คะแนนพร้อมใช้แล้ว
2. **ทดสอบกับ embedding ที่สร้างจากแบบจำลองจริง** เพื่อตรวจสอบว่าผลที่ผูกกับ
   โครงสร้างข้อมูลสังเคราะห์ยังคงอยู่หรือไม่
3. **แยกกลไกที่ทำให้การสร้างดัชนี HNSW ไม่ให้ผลคงที่**
4. **ขยายเครื่องมือตรวจจับให้ครอบคลุมความผิดพลาดที่ต้องเฝ้าขณะเกิดเหตุ**

อยู่ในไฟล์ `FAULTS.md` ของชุดโปรแกรม

## ภาคผนวก ข ผลการทดลองดิบ

ผลการทดลองดิบทั้งหมด 40 ไฟล์ อยู่ในโฟลเดอร์ `results/` ทุกไฟล์มีข้อมูลรุ่นของซอฟต์แวร์
และวันที่กำกับ และผูกกับรหัสการเปลี่ยนแปลงของระบบควบคุมรุ่น

## ภาคผนวก ค บันทึกการตัดสินใจและความผิดพลาดระหว่างการวิจัย


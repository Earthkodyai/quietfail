# บทคัดย่อ

นายพงศกร  หมู่บ้านม่วง

ปีการศึกษา 2569

การวัดและตรวจจับความล้มเหลวเงียบของการค้นหาแบบเวกเตอร์บนระบบจัดการฐานข้อมูล PostgreSQL

ปริญญาวิศวกรรมศาสตรบัณฑิต (สาขาวิศวกรรมคอมพิวเตอร์)  ภาควิชาวิศวกรรมคอมพิวเตอร์
คณะวิศวกรรมศาสตร์  มหาวิทยาลัยเกษตรศาสตร์

---

การค้นหาแบบเวกเตอร์ (vector search) ถูกนำมาใช้อย่างแพร่หลายในระบบสารสนเทศปัจจุบัน
ทั้งในระบบถามตอบที่ดึงข้อมูลจากเอกสาร (retrieval-augmented generation) ระบบแนะนำ
และการค้นหาเชิงความหมาย ระบบเหล่านี้อาศัยดัชนีแบบประมาณ (approximate nearest
neighbor index หรือ ANN index) เพื่อให้ค้นหาได้เร็วพอใช้งานจริง ซึ่งแลกมาด้วยความถูกต้อง
ที่ลดลง ปัญหาสำคัญคือความถูกต้องที่ลดลงนี้**ไม่ปรากฏเป็นข้อผิดพลาดใด ๆ** ระบบยังคืน
ผลลัพธ์ที่มีรูปแบบสมบูรณ์ทุกประการ ผู้พัฒนาจึงไม่มีทางทราบว่าคำตอบที่ควรได้หายไปแล้ว

โครงงานนี้ประยุกต์ระเบียบวิธี **fault injection** เพื่อวัดขนาดของความล้มเหลวเงียบดังกล่าว
บนระบบ PostgreSQL 17.10 ร่วมกับส่วนขยาย pgvector 0.8.5 โดยจงใจสร้างความผิดพลาด
ที่พบได้จริงในการใช้งานจำนวน 12 รูปแบบ แล้ววัดผลเทียบกับเฉลยที่ได้จากการค้นแบบสมบูรณ์
(exact search) ซึ่งเป็นคำตอบที่ถูกต้องตามนิยาม

ผลการทดลองบนข้อมูลสังเคราะห์ 100,000 และ 500,000 รายการ พบว่าที่ค่าตั้งต้นของระบบ
ดัชนีแบบ HNSW ทำให้การค้นหาเร็วขึ้น 117 เท่า แต่คืนคำตอบถูกต้องครบ 10 อันดับแรก
เพียง **2 จาก 200 คำถาม** และทุกรูปแบบการตั้งค่าที่ทดสอบบนข้อมูลชุดนี้
มีคำถามที่ได้คำตอบถูกต้อง **ศูนย์รายการ**

โครงงานได้ทดสอบซ้ำบนข้อมูลจากแบบจำลองสร้างเวกเตอร์จริง เพื่อตรวจสอบว่าข้อสรุป
ผูกกับข้อมูลสังเคราะห์หรือไม่ ผลคือ**ข้อสรุปเชิงกลไกยืนยันได้ทั้งสองชุดข้อมูล
แต่ค่าเชิงปริมาณแตกต่างกันอย่างมีนัยสำคัญ** และข้อสรุปเบื้องต้นของโครงงานเอง
2 จาก 3 ข้อในส่วนที่เกี่ยวกับเอกสารทางการไม่คงอยู่ในรูปเดิม ซึ่งรายงานไว้ครบถ้วน โครงงานยังพบว่าความผิดพลาด 11 จาก 12 รูปแบบสามารถตรวจจับล่วงหน้า
ด้วยโปรแกรมอัตโนมัติได้ โดย 5 รูปแบบตรวจได้จากข้อมูลระบบของฐานข้อมูลเพียงอย่างเดียว
ไม่ต้องใช้ข้อมูลจริงและไม่ต้องรอให้ปัญหาเกิดขึ้นก่อน

นอกจากนี้ยังพบว่าเอกสารทางการของ pgvector ให้ข้อมูลไม่ครบถ้วนในประเด็นความเป็นตัวแทน
ของข้อมูลขณะสร้างดัชนี
ซึ่งตรวจพบจากการวัดทั้งหมด

การทดสอบโค้ดที่สร้างโดยปัญญาประดิษฐ์ ซึ่งเก็บข้อมูล 3 ครั้งจากแบบจำลอง 2 ตัว
พบความล้มเหลวเงียบสองรูปแบบที่ต่างกันโดยสิ้นเชิง คือ *ให้ผลเร็วแต่ไม่ครบถ้วน*
และ *ให้ผลครบถ้วนแต่ไม่ได้ใช้ดัชนีเลย* โดยรูปแบบหลังปรากฏในแบบจำลองทั้งสองตัว
กรณีที่สำคัญที่สุดคือแบบจำลองอธิบายกลไกของปัญหาได้ถูกต้องและตั้งค่าตามเอกสาร
ครบทุกตัว แต่ยังคืนผลลัพธ์ศูนย์รายการ เนื่องจากพารามิเตอร์ที่แก้ปัญหาได้จริง
ไม่ปรากฏในเอกสาร นอกจากนี้การเก็บข้อมูลซ้ำด้วยโจทย์ชุดเดิมยังพบว่าผลไม่คงที่
ซึ่งเป็นเหตุให้โครงงานรายงานผลข้อนี้เป็นการจำแนกรูปแบบ มิใช่เป็นอัตรา

ผลผลิตของโครงงานประกอบด้วยชุดทดลองที่ทำซ้ำได้ เครื่องมือตรวจจับที่ใช้กับฐานข้อมูลอื่นได้
และรายงานผลพร้อมข้อจำกัด

**คำสำคัญ:** ความล้มเหลวเงียบ, การค้นหาแบบเวกเตอร์, การฉีดความผิดพลาด, ค่าเรียกคืน,
ฐานข้อมูลเชิงสัมพันธ์, การประกันคุณภาพซอฟต์แวร์

# ABSTRACT

Pongsakorn  Mubanmuang

Academic Year 2026

Measurement and Detection of Silent Failures in Vector Search on PostgreSQL

Bachelor Degree in Computer Engineering. Department of Computer Engineering.
Faculty of Engineering, Kasetsart University.

---

Vector search underpins a growing share of modern information systems, including
retrieval-augmented generation, recommendation, and semantic search. These systems
rely on approximate nearest neighbor (ANN) indexes to achieve practical query
latency, trading correctness for speed. The critical problem is that this loss of
correctness **raises no error**. The system returns a structurally complete result
set, so developers have no signal that answers are missing.

This research applies **fault injection** to measure the magnitude of such silent
failures on PostgreSQL 17.10 with the pgvector 0.8.5 extension. Twelve realistic
misconfigurations were deliberately introduced and measured against ground truth
obtained from exact search, which is correct by definition.

On synthetic datasets of 100,000 and 500,000 records, an HNSW index at default
settings was 117 times faster while returning a fully correct top-10 for only
**2 of 200 queries**. Every configuration tested contained queries returning **zero**
correct results. Eleven of the twelve fault types proved automatically detectable in
advance; five require only database catalog inspection, needing neither production
data nor a prior incident.

The work additionally identified three points where the official pgvector
documentation is incorrect or incomplete, all found through measurement. Testing of
AI-generated code found traps in 5 of 10 tasks; most notably, the model correctly
described the failure mechanism and applied every documented remedy, yet still
returned zero rows, because the parameter that actually resolves the problem is
absent from the documentation.

Deliverables comprise a reproducible test harness, a portable detection tool, and a
results report with stated limitations.

**Keywords:** silent failure, vector search, fault injection, recall, relational
database, software quality assurance

# บทที่ 1 บทนำ

## 1.1 ความสำคัญของปัญหา

ระบบสารสนเทศจำนวนมากในปัจจุบันนำการค้นหาแบบเวกเตอร์มาใช้เป็นองค์ประกอบหลัก
กลไกการทำงานคือการแปลงข้อมูลแต่ละรายการเป็นเวกเตอร์ตัวเลขที่สะท้อนความหมาย
(embedding) แล้วค้นหาโดยวัดระยะห่างระหว่างเวกเตอร์ รายการที่มีความหมายใกล้เคียงกัน
จะมีเวกเตอร์อยู่ใกล้กันในปริภูมิหลายมิติ

เมื่อข้อมูลมีจำนวนมาก การเปรียบเทียบกับทุกรายการมีต้นทุนสูงเกินกว่าจะใช้งานได้จริง
แนวทางมาตรฐานจึงใช้ดัชนีแบบ ANN ซึ่งลดจำนวนรายการที่ต้องเปรียบเทียบลง
โดยยอมรับว่าผลลัพธ์อาจไม่ครบถ้วน

ประเด็นที่โครงงานนี้ให้ความสำคัญคือ **ลักษณะของความล้มเหลว** ไม่ใช่ตัวความล้มเหลวเอง

ฐานข้อมูลเชิงสัมพันธ์แบบดั้งเดิมเมื่อมีการใช้งานผิดพลาด มักแสดงข้อผิดพลาดออกมา
หรือให้ผลลัพธ์ที่ผิดในลักษณะที่สังเกตเห็นได้ แต่การค้นหาแบบเวกเตอร์ที่ตั้งค่าไม่เหมาะสม
จะคืนผลลัพธ์ที่มีจำนวนแถวสมเหตุสมผล มีโครงสร้างถูกต้อง และเรียงลำดับอย่างเป็นระบบ
ต่างกันเพียงว่ารายการที่ควรปรากฏบางส่วนหายไป

ผู้พัฒนาจึงไม่ได้รับสัญญาณเตือนใด ๆ ระบบเฝ้าระวังไม่แจ้งเหตุ และปัญหามักถูกค้นพบ
เมื่อผู้ใช้ปลายทางรายงานว่าค้นหาไม่พบสิ่งที่ควรพบ ซึ่งเป็นเวลาที่สายเกินกว่าจะแก้ไข
ได้โดยไม่กระทบผู้ใช้

เอกสารทางการของ pgvector ระบุไว้เองว่าการเพิ่มดัชนีแบบประมาณ *เปลี่ยนผลลัพธ์ของ
คำสั่งค้นหา* ไม่ใช่เพียงทำให้เร็วขึ้น โครงงานนี้จึงไม่ได้มุ่งค้นพบว่าปัญหามีอยู่จริงหรือไม่
แต่มุ่ง **วัดขนาดของปัญหา** และ **สร้างวิธีตรวจจับล่วงหน้า** ซึ่งเป็นสิ่งที่ยังไม่ปรากฏ
ในงานที่มีอยู่

## 1.2 วัตถุประสงค์ของโครงงาน

1. เพื่อวัดปริมาณผลลัพธ์ที่สูญหายจากการตั้งค่าดัชนี ANN ที่ไม่เหมาะสม โดยไม่มีการแจ้ง
   ข้อผิดพลาด เปรียบเทียบกับผลจากการค้นแบบสมบูรณ์
2. เพื่อพัฒนาและประเมินวิธีตรวจจับความผิดพลาดดังกล่าวโดยอัตโนมัติ พร้อมระบุว่า
   แต่ละวิธีอาศัยหลักฐานประเภทใด
3. เพื่อจำแนกรูปแบบความล้มเหลวเงียบที่ปรากฏในโค้ดที่สร้างโดยปัญญาประดิษฐ์
   และตรวจสอบว่ารูปแบบดังกล่าวเกิดซ้ำข้ามตัวแบบและข้ามการถามหรือไม่

## 1.3 คำถามของโครงงาน

| ข้อ | คำถาม | ตัวชี้วัด |
|---|---|---|
| RQ1 | การตั้งค่าดัชนี ANN ที่ผิดพลาดโดยไม่เกิดข้อผิดพลาด ทำให้ผลลัพธ์คลาดเคลื่อนเพียงใด | ค่าเรียกคืน (recall@k) เทียบกับการค้นแบบสมบูรณ์ |
| RQ2 | ความผิดพลาดเหล่านี้ตรวจจับอัตโนมัติได้จำนวนเท่าใด และจากหลักฐานประเภทใด | จำนวนรูปแบบที่มีตัวตรวจซึ่งพิสูจน์แล้วว่าจำแนกสถานะได้ |
| RQ3 | โค้ดที่สร้างโดยปัญญาประดิษฐ์ปรากฏความล้มเหลวเงียบใน**รูปแบบใดบ้าง** และรูปแบบดังกล่าว**เกิดซ้ำข้ามตัวแบบและข้ามการถามหรือไม่** | การจำแนกชนิดความล้มเหลวจากชุดโจทย์ควบคุม โดยประมวลผลคำสั่งจริงและตรวจแผนการทำงานของคำสั่ง ร่วมกับการเก็บข้อมูลซ้ำเพื่อประเมินความเสถียร |

RQ1 เป็นคำถามหลัก RQ2 เป็นสิ่งที่ทำให้ผลงานอยู่ในรูปเครื่องมือที่นำไปใช้ได้
RQ3 เป็นส่วนขยายที่เชื่อมโยงกับบริบทการพัฒนาซอฟต์แวร์ในปัจจุบัน

**หมายเหตุเชิงระเบียบวิธีของ RQ3** ผู้พัฒนากำหนด RQ3 ให้เป็นคำถาม**เชิงจำแนกรูปแบบ**
มิใช่คำถามเชิงความถี่ เนื่องจากชุดโจทย์ที่ใช้ถูกออกแบบขึ้นเพื่อมุ่งไปยังกับดักที่ทราบล่วงหน้า
จึงมิได้เป็นตัวอย่างสุ่มจากประชากรของงานพัฒนาจริง การรายงานผลเป็นสัดส่วนหรืออัตรา
จะเป็นการอนุมานเกินกว่าที่วิธีการรองรับ แม้เพิ่มจำนวนโจทย์ก็ไม่แก้ปัญหานี้
เพราะข้อจำกัดอยู่ที่**วิธีคัดเลือกโจทย์** มิใช่ที่ขนาดตัวอย่าง

ทั้งนี้การเก็บข้อมูลซ้ำได้แสดงให้เห็นว่าการวัดเพียงครั้งเดียวไม่เสถียร
และผลจากการเก็บซ้ำได้เปลี่ยนข้อสรุปของงานจริง ดังรายละเอียดในบทที่ 5

## 1.4 ขอบเขตของโครงงาน

**สิ่งที่ศึกษา**

- ระบบ PostgreSQL รุ่น 17.10 ร่วมกับ pgvector รุ่น 0.8.5 ระบุรุ่นแบบเจาะจงในทุกผลการทดลอง

- ข้อมูลสังเคราะห์ที่ควบคุมการกระจายตัวได้ เพื่อให้ทราบเฉลยอย่างแน่นอน

| การเปรียบเทียบแบบจำลองสร้าง embedding หลายตัว | เป็นคำถามวิจัยคนละประเด็น |
| ข้อมูลจากระบบใช้งานจริง | ไม่สามารถทราบเฉลยที่ถูกต้องได้ ซึ่งเป็นข้อบังคับของระเบียบวิธี |

3. ชุดทดลองที่ทำซ้ำได้ สำหรับใช้เป็นฐานในการศึกษาต่อ

# บทที่ 2 ทฤษฎีและงานที่เกี่ยวข้อง

## 2.1 การค้นหาเพื่อนบ้านใกล้ที่สุดแบบประมาณ

ปัญหาการค้นหาเพื่อนบ้านใกล้ที่สุด (nearest neighbor search) คือการหารายการ k รายการ
ที่มีระยะห่างจากจุดคำถามน้อยที่สุด การแก้ปัญหาแบบสมบูรณ์ต้องคำนวณระยะห่างกับทุกรายการ
ซึ่งมีความซับซ้อนเชิงเส้นตามจำนวนข้อมูล

ในปริภูมิมิติสูง โครงสร้างข้อมูลแบบแบ่งปริภูมิดั้งเดิมสูญเสียประสิทธิภาพ จึงเกิดแนวทาง
**การค้นหาแบบประมาณ** ซึ่งยอมรับว่าผลลัพธ์อาจไม่ใช่เพื่อนบ้านที่ใกล้ที่สุดจริง
เพื่อแลกกับความเร็วที่เพิ่มขึ้นหลายสิบถึงหลายร้อยเท่า

ตัวชี้วัดคุณภาพมาตรฐานคือ **ค่าเรียกคืน (recall@k)** นิยามเป็นสัดส่วนของรายการที่ถูกต้อง
ซึ่งปรากฏในผลลัพธ์ k อันดับแรก เทียบกับผลจากการค้นแบบสมบูรณ์

## 2.2 ดัชนีที่ศึกษาในโครงงานนี้

### 2.2.1 HNSW

Hierarchical Navigable Small World สร้างกราฟหลายชั้นที่เชื่อมโยงรายการที่อยู่ใกล้กัน
การค้นหาเริ่มจากชั้นบนซึ่งเชื่อมโยงแบบกระโดดไกล แล้วไล่ลงชั้นล่างที่ละเอียดขึ้น

พารามิเตอร์สำคัญขณะค้นหาคือ `hnsw.ef_search` ซึ่งกำหนดขนาดรายการผู้เข้ารอบ
ที่ระบบเก็บไว้ระหว่างการเดินกราฟ ค่าตั้งต้นใน pgvector 0.8.5 คือ **40**

### 2.2.2 IVFFlat

Inverted File with Flat compression แบ่งข้อมูลออกเป็นกลุ่มด้วยขั้นตอนวิธี k-means
ขณะสร้างดัชนี การค้นหาจะเปรียบเทียบเฉพาะกลุ่มที่มีจุดศูนย์กลางใกล้คำถามที่สุด

พารามิเตอร์สำคัญคือ `lists` (จำนวนกลุ่ม) ขณะสร้าง และ `ivfflat.probes` (จำนวนกลุ่ม
ที่เปิดค้น) ขณะค้นหา ค่าตั้งต้นของ `probes` คือ **1** ขณะที่เอกสารแนะนำ `sqrt(lists)`

### 2.2.3 ข้อสังเกตเชิงโครงสร้างของค่าตั้งต้น

`ef_search` เป็นค่าสัมบูรณ์ที่ไม่เปลี่ยนตามขนาดข้อมูล ขณะที่ `probes` เป็นค่าสัมพัทธ์
กับจำนวนกลุ่ม ความแตกต่างนี้ทำให้ดัชนีสองชนิดเสื่อมคุณภาพตามขนาดข้อมูลในลักษณะ
ที่ต่างกัน ซึ่งเป็นประเด็นที่ผลการทดลองในบทที่ 5 ยืนยัน

## 2.3 ข้อจำกัดที่เอกสารทางการระบุไว้

การทบทวนเอกสารของ pgvector รุ่น 0.8.5 พบข้อกำหนดที่เกี่ยวข้องโดยตรง ดังนี้

1. รูปแบบคำสั่งค้นหาต้องมี `ORDER BY` ตามด้วย distance operator โดยตรง และมี `LIMIT`
   จึงจะใช้ดัชนีได้ การห่อ operator ด้วยนิพจน์ใด ๆ ทำให้ดัชนีถูกข้าม
2. ต้องสร้างดัชนีแยกต่างหากสำหรับแต่ละฟังก์ชันระยะทาง โดยใช้ operator class ที่ตรงกัน
3. การกรองด้วยเงื่อนไข `WHERE` ทำงาน **หลัง** ดัชนีคืนรายการผู้เข้ารอบแล้ว
4. เวกเตอร์ที่เป็นค่าว่างไม่ถูกบรรจุในดัชนี และเวกเตอร์ศูนย์ไม่ถูกบรรจุเมื่อใช้ระยะทางแบบ cosine
5. แถวที่ถูกลบแล้วแต่ยังไม่ถูกเก็บกวาดอาจทำให้ผลลัพธ์ที่ได้น้อยลง
6. โหมดค้นต่อเนื่อง (iterative scan) มีตั้งแต่รุ่น 0.8.0 แต่ยังปิดเป็นค่าตั้งต้น

ข้อกำหนดเหล่านี้ถูกใช้เป็นฐานในการออกแบบความผิดพลาดที่จะฉีดในบทที่ 4

# บทที่ 4 วิธีการดำเนินโครงงาน

## 4.1 ข้อมูลที่ใช้ทดลอง

### 4.1.1 ลักษณะและที่มา

ข้อมูลเป็นเวกเตอร์สังเคราะห์ขนาด 384 มิติ จัดกลุ่มตามความหมายเป็น 50 กลุ่ม
สร้างด้วยสูตรที่กำหนดผลลัพธ์ได้แน่นอน (deterministic) โดยคำนวณจากค่าแฮชของคีย์
ไม่ใช้ฟังก์ชันสุ่มที่ขึ้นกับลำดับการเรียก จึงสร้างซ้ำได้ผลเดิมทุกครั้ง

| รายการ | ค่า |
|---|---|
| ขนาดข้อมูล | 100,000 และ 500,000 รายการ |
| มิติ | 384 |
| จำนวนกลุ่ม | 50 |
| ชุดคำถามทดสอบ | 200 คำถาม ครอบคลุมครบทุกกลุ่ม |
| ฟังก์ชันระยะทาง | cosine |

### 4.1.2 เหตุผลที่ใช้ข้อมูลสังเคราะห์

ระเบียบวิธีของงานนี้ต้องการ **เฉลยที่ถูกต้องแน่นอน** เพื่อใช้เป็นฐานเปรียบเทียบ
ข้อมูลจากระบบใช้งานจริงไม่สามารถให้เฉลยเช่นนี้ได้ เนื่องจากไม่มีผู้ใดทราบว่าคำตอบ
ที่ถูกต้องคืออะไร การใช้ข้อมูลสังเคราะห์จึงเป็นข้อบังคับของระเบียบวิธี ไม่ใช่การลดทอน

### 4.1.3 การตรวจสอบความสมเหตุสมผลของข้อมูล

ก่อนใช้ข้อมูลชุดใดวัดผล ต้องผ่านการตรวจสองประการ

1. **ค่าลายนิ้วมือ (fingerprint)** ของทั้งชุดข้อมูลและชุดคำถาม ต้องตรงกับค่าที่บันทึกไว้
   เพื่อยืนยันว่าไม่มีการแก้ไขภายหลัง
2. **ระยะห่างภายในกลุ่มกับข้ามกลุ่มต้องแยกจากกันชัดเจน** วัดได้ 0.3820 และ 0.9997
   ตามลำดับ (ห่างกัน 2.6 เท่า) หากสองค่านี้ใกล้กัน แปลว่าข้อมูลไม่มีโครงสร้างเชิงกลุ่มจริง
   และค่าเรียกคืนที่วัดได้จะไม่มีความหมาย

การตรวจข้อที่สองมีที่มาจากความผิดพลาดที่เกิดขึ้นจริงระหว่างพัฒนา ซึ่งบันทึกไว้ในบทที่ 5

## 4.2 การกำหนดเฉลย

เฉลยของโครงงานนี้มาจากสองกลไกที่ทำงานร่วมกัน

**กลไกที่ 1 การฉีดความผิดพลาด** ผู้พัฒนาเป็นผู้สร้างความผิดพลาดขึ้นเอง จึงทราบสาเหตุ
อย่างแน่นอน ไม่ต้องอนุมานจากอาการ ทุกความผิดพลาดมีเงื่อนไขตรวจสอบ (assertion) กำกับ
หากฉีดแล้วไม่เกิดผลตามที่ออกแบบ สคริปต์จะยุติด้วยข้อผิดพลาด ไม่อนุญาตให้บันทึกผล

**กลไกที่ 2 การค้นแบบสมบูรณ์เป็นเฉลยของค่าเรียกคืน** ใช้วิธีที่เอกสารทางการแนะนำ

```sql
BEGIN;
SET LOCAL enable_indexscan = off;
SELECT ... ORDER BY embedding <=> $1 LIMIT $2;
COMMIT;
```

วิธีนี้บังคับให้ระบบเปรียบเทียบทุกรายการ ผลที่ได้จึงถูกต้องตามนิยาม และไม่เปลี่ยนแปลง
สภาพฐานข้อมูล ต่างจากการลบดัชนีทิ้งซึ่งกระทบการทดลองอื่น

## 4.3 การเลือกค่า k ในการวัด

โครงงานนี้ใช้ recall@10 เป็นตัวชี้วัดหลัก เนื่องจากเป็นหน่วยเดียวกับที่ระบบจริง
ส่งมอบผลลัพธ์ กล่าวคือ ระบบถามตอบที่ดึงข้อมูลจากเอกสารมักใช้เอกสารประกอบ 5 ถึง 10 ชิ้น
ต่อหนึ่งคำถาม หน้าแสดงผลการค้นหาและระบบแนะนำแสดงประมาณ 10 รายการแรก และผู้ใช้
มักไม่ดูเกินหน้าแรก การวัดที่ 10 อันดับแรกจึงสะท้อนสิ่งที่ถึงมือผู้ใช้จริง

มีการวัดที่ 100 อันดับควบคู่ เพื่อสังเกตพฤติกรรมเมื่อขอผลลัพธ์จำนวนมากขึ้น

## 4.4 ชุดความผิดพลาดที่ศึกษา

รูปแบบเดิมออกพร้อมบันทึกเหตุผล เพื่อป้องกันการเลือกเฉพาะผลที่สนับสนุนข้อสรุป

| ช่วง | รหัส | ลักษณะความผิดพลาด |

| | I03 | สร้างดัชนีโดยไม่ใช้โหมดไม่ปิดกั้น ทำให้การเขียนถูกปิดกั้น |
| | I04 | สร้างดัชนีใหม่บนข้อมูลเดิมแล้วได้คำตอบไม่เหมือนเดิม |
| | I05 | หน่วยความจำสำหรับสร้างดัชนีไม่พอ |
| **เรียกใช้** | Q01 | การสูญเสียค่าเรียกคืนที่ค่าตั้งต้น (การวัดหลัก) |
| | Q02 | รูปแบบคำสั่งทำให้ดัชนีไม่ถูกใช้ |

กลไกการวัดใช้ได้ทั้งกับฐานข้อมูลทั่วไปและกับการค้นหาแบบเวกเตอร์

## 4.5 กระบวนการทำงานต่อหนึ่งความผิดพลาด

1. เขียนนิยามให้ครบ 5 ส่วน ได้แก่ อาการ สาเหตุ วิธีฉีด เฉลย และเงื่อนไขตรวจสอบ
2. เขียนโปรแกรมฉีดความผิดพลาด
3. เขียนไฟล์เฉลยพร้อมข้อมูลรุ่นและวันที่
4. เพิ่มตัวตรวจจับ
5. รันติดต่อกัน 3 รอบ และบันทึกผลดิบ
6. **พิสูจน์ว่าตัวตรวจจับจำแนกสถานะได้จริง** ต้องแสดงได้ทั้งกรณีพบและไม่พบ
7. ตรวจความสอดคล้องทั้งโครงการด้วยโปรแกรมอัตโนมัติ

ขั้นตอนที่ 6 เป็นข้อกำหนดที่แยกจากขั้นตอนที่ 5 อย่างชัดเจน เนื่องจากเงื่อนไขตรวจสอบ
ตอบคำถามว่า *ความผิดพลาดเกิดขึ้นจริงหรือไม่* ขณะที่ขั้นตอนที่ 6 ตอบคำถามว่า
*ตัวตรวจจับใช้การได้หรือไม่* ตัวตรวจจับที่ตอบว่าพบปัญหาเสมอไม่ว่าสภาพใด
ไม่ได้วัดสิ่งใดเลย

## 4.6 การออกแบบตัวตรวจจับ

ตัวตรวจจับให้ผลลัพธ์ **3 สถานะ** ไม่ใช่ 2 สถานะ

| สถานะ | ความหมาย |
|---|---|
| `DETECTED` | ตรวจแล้วพบปัญหา |
| `NOT_DETECTED` | ตรวจแล้วไม่พบปัญหา |
| `CANNOT_CHECK` | **ตรวจไม่ได้** เช่น ไม่มีดัชนีให้ตรวจ หรือไม่มีข้อมูลที่จำเป็น |

การแยกสถานะที่สามออกมาเป็นหลักการสำคัญของงานนี้ เครื่องมือที่รายงานว่าระบบปลอดภัย
ทั้งที่ไม่ได้ตรวจสิ่งใดเลย มีอันตรายมากกว่าการไม่มีเครื่องมือ เพราะสร้างความเชื่อมั่นที่ผิด

ตัวอย่างที่ตัวตรวจจับปฏิเสธการให้คำตอบ

- ตัวตรวจของ Q03 และ L02 ปฏิเสธเมื่อจำนวนผลลัพธ์ที่ขอไม่ต่ำกว่า `ef_search`
  เนื่องจากจะแยกจากความผิดพลาด Q06 ไม่ได้
- ตัวตรวจของ I04 ปฏิเสธเมื่อไม่มีบันทึกว่าค่าเรียกคืนถูกวัดบนดัชนีรุ่นใด
- ตัวตรวจของ I05 ปฏิเสธเมื่อมิติของข้อมูลต่างจากที่ปรับเทียบค่าไว้

## 4.7 การควบคุมคุณภาพของกระบวนการ

**การรันซ้ำ** ทุกการวัดรันติดต่อกัน 3 รอบ ส่วนที่เกี่ยวกับการสร้างดัชนีซึ่งพิสูจน์แล้วว่า
ไม่ให้ผลเหมือนเดิม ต้องสร้างซ้ำ 5 รอบต่อหนึ่งการตั้งค่า และรายงานเป็นช่วงค่า
พร้อมผลรายคำถาม ไม่ใช่เพียงค่าเฉลี่ย

**ตัวชี้วัดด้านทรัพยากร** ใช้จำนวนบล็อกที่อ่าน (buffers) เป็นหลัก แทนการใช้เวลา
เนื่องจากเวลาแปรผันตามฮาร์ดแวร์ได้หลายเท่า ขณะที่จำนวนบล็อกเป็นค่าเชิงโครงสร้าง

**การตรวจสอบทั้งโครงการ** มีโปรแกรมตรวจความสอดคล้อง 33 หัวข้อ ครอบคลุมความครบถ้วน
ของหลักฐาน ความตรงกันระหว่างเอกสาร สภาพฐานข้อมูล และความสามารถในการทำงาน
ของตัวนับคะแนน ใช้เวลาประมาณ 30 วินาที

## 4.8 การทดสอบโค้ดที่สร้างโดยปัญญาประดิษฐ์

สร้างชุดโจทย์ 10 ข้อที่มีลักษณะเหมือนงานจริง โดยไม่มีคำใบ้เกี่ยวกับดัชนีหรือการปรับแต่ง
แต่ละโจทย์ถามในบทสนทนาแยกกัน ใช้คำตอบแรกโดยไม่ถามซ้ำ

เก็บข้อมูลรวม 3 ครั้งจากแบบจำลอง 2 ตัว โดย**แบบจำลองตัวแรกเก็บซ้ำ 2 รอบ
ด้วยโจทย์ชุดเดิมทุกตัวอักษรในบทสนทนาใหม่** เพื่อประเมินความเสถียรของการวัด
ซึ่งเป็นไปตามหลักการเดียวกับที่โครงงานนี้กำหนดให้การทดลองทุกรายการต้องทำซ้ำ

แบบจำลองที่ใช้ประกอบด้วย **แบบจำลอง ก** คือ Claude Opus 5 ตั้งค่าระดับการให้เหตุผลสูง
เก็บข้อมูล 2 รอบ และ **แบบจำลอง ข** คือ ChatGPT ผ่านส่วนต่อประสานเว็บทั่วไป เก็บข้อมูล 1 รอบ
ทั้งนี้แบบจำลอง ข มิได้ระบุรุ่นที่แน่นอนได้ จึงทำซ้ำให้ตรงทุกประการไม่ได้
ซึ่งเป็นข้อจำกัดที่ระบุไว้ในหัวข้อ 6.2

การให้คะแนนใช้วิธี **นำคำสั่งที่ได้ไปรันจริงบนฐานข้อมูล** แล้ววัดผลเทียบกับการค้นแบบสมบูรณ์
ไม่ใช่การตรวจรูปแบบของคำสั่ง เนื่องจากคำสั่งที่มีรูปแบบถูกต้องทุกประการยังคืนผลลัพธ์
ไม่ครบได้ ดังที่ความผิดพลาด Q03 แสดงไว้

นอกจากนั้นการให้คะแนนยัง**ตรวจแผนการทำงานของคำสั่ง (query plan) ว่ามีการใช้ดัชนี
เวกเตอร์จริงหรือไม่** เนื่องจากตัวให้คะแนนรุ่นแรกซึ่งวัดเพียงจำนวนรายการและค่าเรียกคืน
ได้ตัดสินว่าคำตอบชุดหนึ่งผ่านเกณฑ์ 8 จาก 10 ข้อ ทั้งที่คำตอบดังกล่าวไม่ได้ใช้ดัชนีเลย
จึงเป็นการค้นแบบสมบูรณ์ซึ่งย่อมได้ผลครบถ้วนเสมอ ข้อบกพร่องนี้ตรวจพบเพราะผลที่ได้
ขัดแย้งกับเพดานที่ความผิดพลาด Q06 กำหนดไว้

**ข้อจำกัดเชิงระเบียบวิธีที่ต้องระบุ** ชุดโจทย์นี้ออกแบบขึ้นเพื่อมุ่งไปยังกับดักที่ทราบ
ล่วงหน้า จึงมิใช่ตัวอย่างสุ่มจากงานพัฒนาจริง ผลจากส่วนนี้จึงรายงานเป็นการจำแนกรูปแบบ
ความล้มเหลวและความเสถียรของรูปแบบ มิใช่รายงานเป็นอัตราหรือสัดส่วน

# บทที่ 5 ผลการดำเนินโครงงานและวิจารณ์

## 5.1 ผลตอบคำถามของโครงงานข้อที่ 1

การวัดใช้ค่าตั้งต้นของระบบทั้งหมด (`ef_search` = 40, `probes` = 1) ซึ่งเป็นสภาพที่พบ
ได้บ่อยที่สุดในระบบใช้งานจริง

### 5.1.2 ดัชนีสองชนิดเสื่อมคุณภาพตามขนาดข้อมูลต่างกัน

### 5.1.3 ความเร็วเพิ่มขึ้นพร้อมกับคุณภาพที่ลดลง

อัตราเร่งของ HNSW เพิ่มจาก 32.6 เท่าเป็น 117.1 เท่าเมื่อข้อมูลเพิ่มขึ้น ในขณะที่

ในช่วงเวลาที่คุณภาพกำลังเสื่อมลง

### 5.1.4 การเปรียบเทียบข้ามระบบ

เพื่อตรวจสอบว่าปรากฏการณ์นี้เป็นลักษณะเฉพาะของ pgvector หรือไม่ ได้ทำการวัดซ้ำ
บน Qdrant 1.12.4 โดยใช้ข้อมูล ชุดคำถาม และเฉลยชุดเดียวกัน

**ตารางที่ 2** การเปรียบเทียบข้ามระบบที่ขนาดข้อมูล 100,000 รายการ

| ระบบ | recall@10 | recall@100 |
|---|---|---|
| pgvector HNSW (`ef_search` = 40) | 0.8565 | 0.3903 |
| Qdrant HNSW (`hnsw_ef` = 40) | 0.9945 | 0.9895 |
| Qdrant ค่าตั้งต้นของระบบเอง | 1.0000 | 0.9996 |

ผลแสดงว่าการสูญเสียค่าเรียกคืนเกิดขึ้นกับทั้งสองระบบ (Qdrant มีค่าต่ำสุดต่อคำถาม
เท่ากับ 0.90 และได้ครบถ้วนเพียง 69 จาก 200 คำถามที่ k = 100) จึงสรุปได้ว่าเป็น
คุณลักษณะของการค้นหาแบบประมาณ ไม่ใช่ข้อบกพร่องเฉพาะของ pgvector

อย่างไรก็ตาม **ขนาดของความเสียหายต่างกันอย่างมีนัยสำคัญ** ค่า recall@100 ที่ต่ำมาก
ของ pgvector เกิดจากการที่ระบบยอมให้ `ef_search` มีค่าน้อยกว่าจำนวนผลลัพธ์ที่ขอ
การทบทวนเอกสารของระบบอื่นพบว่า Milvus กำหนด `ef` เท่ากับจำนวนผลลัพธ์ที่ขอ
Weaviate ปรับค่าอัตโนมัติ และ OpenSearch กับเครื่องมือ lucene บังคับให้เท่ากับ k

## 5.2 ผลตอบคำถามของโครงงานข้อที่ 2

ความผิดพลาด 15 รูปแบบมีทั้งโปรแกรมฉีดและตัวตรวจจับครบถ้วน คิดเป็น 11 จาก 12 รูปแบบ

## 5.3 ความสัมพันธ์ระหว่างผลการวัดกับเอกสารทางการ

ผลส่วนนี้ไม่ได้อยู่ในวัตถุประสงค์เดิม แต่ปรากฏขึ้นจากการวัดตามกระบวนการปกติ

**หัวข้อนี้ได้รับการแก้ไขหลังการทดสอบซ้ำบนข้อมูลจากแบบจำลองจริง** ข้อสรุปเดิม
ระบุว่าเอกสารทางการไม่ถูกต้องหรือไม่ครบถ้วน 3 จุด เมื่อทดสอบข้ามชุดข้อมูลแล้ว
**ข้อสรุป 2 จาก 3 ข้อไม่คงอยู่ในรูปเดิม** ดังรายละเอียดในแต่ละหัวข้อย่อย

ผู้พัฒนารายงานผลนี้ไว้ทั้งหมดโดยไม่ตัดออก เนื่องจากเป็นตัวอย่างโดยตรงของ
ข้อจำกัดที่โครงงานระบุไว้เองในหัวข้อ 6.2 ว่าผลบางส่วนผูกกับข้อมูลสังเคราะห์
และเป็นเหตุผลว่าเหตุใดการทดสอบข้ามชุดข้อมูลจึงจำเป็น มิใช่ทางเลือก

### 5.3.2 ระบบไม่มีคำเตือนสำหรับตัวอย่างที่ไม่เป็นตัวแทน

เงื่อนไข ง บนข้อมูลจริงนิยามเป็น *เพื่อนบ้านที่ใกล้จุดยึดที่สุด 1,000 รายการ*
เนื่องจากข้อมูลจากแบบจำลองจริงไม่มีกลุ่มที่ผู้พัฒนาออกแบบไว้

**ข้อค้นพบที่ยืนยันได้ทั้งสองชุดข้อมูล** คือความเป็นตัวแทนของตัวอย่างขณะสร้างดัชนี
มีผลมากกว่าจำนวนรายการ เมื่อควบคุมจำนวนรายการให้เท่ากันที่ 1,000 รายการ
ตัวอย่างที่กระจุกตัวให้ค่าเรียกคืนต่ำกว่าตัวอย่างที่กระจาย และมีคำค้นที่ไม่ได้ผลลัพธ์
ที่ถูกต้องเลยมากกว่าเท่าตัว ทั้งนี้ระบบไม่มีคำเตือนใด ๆ สำหรับกรณีดังกล่าว
เนื่องจากคำเตือนผูกกับเงื่อนไขจำนวนแถวน้อยกว่าจำนวนกลุ่มเพียงอย่างเดียว
ซึ่งมิใช่ตัวแปรที่กำหนดผล

**ข้อค้นพบที่ไม่ยืนยันข้ามชุดข้อมูล** คือข้อสรุปเดิมที่ว่าคำเตือนปรากฏในกรณีที่ดีที่สุด
บนข้อมูลสังเคราะห์เงื่อนไข ก ให้ค่าเรียกคืนสมบูรณ์ แต่บนข้อมูลจริงกลับให้ค่าต่ำเป็น
อันดับสอง คำเตือนจึงปรากฏถูกกรณี และข้อความในคำเตือนที่ระบุว่าจะทำให้ค่าเรียกคืนต่ำ
ก็เป็นจริงบนข้อมูลจริง

สาเหตุของความแตกต่างระบุได้ชัดเจน คือข้อมูลสังเคราะห์เรียงรหัสสลับกลุ่ม
ตัวอย่าง 50 รายการแรกจึงครอบคลุมครบทุกกลุ่มพอดี ซึ่งเป็นคุณสมบัติของชุดข้อมูลนั้น
มิใช่หลักการทั่วไป ผู้พัฒนาได้บันทึกข้อสงสัยนี้ไว้ตั้งแต่ขั้นวัดผล และการทดสอบ
บนข้อมูลจริงได้ยืนยันว่าข้อสงสัยดังกล่าวถูกต้อง

นอกจากนี้ยังพบผลที่ข้อมูลสังเคราะห์ไม่แสดง คือเงื่อนไข ก ให้ผลคงที่สมบูรณ์
ทั้ง 5 รอบ (พิสัยเท่ากับศูนย์) ขณะที่เงื่อนไขอื่นแปรผัน เนื่องจากจำนวนรายการ
น้อยกว่าจำนวนกลุ่มที่กำหนด ขั้นตอนวิธี k-means จึงไม่มีองค์ประกอบสุ่มเหลืออยู่
**กรณีเดียวกับที่ระบบเตือน จึงเป็นกรณีเดียวที่ผลทำซ้ำได้อย่างสมบูรณ์**

### 5.3.3 วิธีแก้ปัญหาที่เอกสารระบุไม่เพียงพอ แม้ดำเนินการครบทุกข้อ

**ตารางที่ 6** ผลของการปรับพารามิเตอร์ทีละตัว ที่เงื่อนไขกรองตรง 1 เปอร์เซ็นต์ ขอ 40 รายการ
เปรียบเทียบข้อมูลสังเคราะห์กับข้อมูลจากแบบจำลองจริง

| การปรับ | สังเคราะห์ | **จริง** | บล็อกที่อ่าน (จริง) |
|---|---|---|---|
| ค่าตั้งต้นทั้งหมด | 0 | 1 | 530 |
| เปิดโหมดค้นต่อเนื่อง (`iterative_scan`) | 0 | 5 | 873 |
| เพิ่ม `max_scan_tuples` 10 เท่า | 0 | **5** | **873** |
| เพิ่ม `scan_mem_multiplier` 8 เท่า | 0 | 13 | 3,005 |
| **เพิ่ม `work_mem` จาก 64 กิโลไบต์เป็น 4 เมกะไบต์** | **40** | **40** | 27,917 |

**ข้อค้นพบนี้ยืนยันได้ทั้งสองชุดข้อมูล** พารามิเตอร์ที่เอกสารระบุไว้เป็นวิธีแก้
ไม่มีข้อใดทำให้ได้ผลลัพธ์ครบถ้วน ผลจะครบก็ต่อเมื่อเพิ่มค่า `work_mem`
ซึ่งเป็นพารามิเตอร์ทั่วไปของระบบฐานข้อมูล มิใช่ของส่วนขยาย pgvector
และไม่ปรากฏในรายการเงื่อนไขที่เอกสารระบุไว้

ผู้พัฒนาได้ปรับถ้อยคำจากข้อสรุปเดิมที่ระบุว่าวิธีแก้ *ไม่ทำงานเลย* เนื่องจาก
บนข้อมูลจริงพารามิเตอร์เหล่านั้นช่วยได้บางส่วน แต่ไม่เคยทำให้ผลครบถ้วน
ข้อสรุปที่ถูกต้องจึงเป็น **ไม่เพียงพอแม้ดำเนินการครบทุกข้อ**

นอกจากนี้ยังพบว่าพารามิเตอร์ `max_scan_tuples` **ไม่ให้ผลใด ๆ ในทั้งสองชุดข้อมูล**
เมื่อเพิ่มค่าขึ้น 10 เท่า จำนวนบล็อกที่อ่านไม่เปลี่ยนแปลงแม้แต่บล็อกเดียว
และจำนวนผลลัพธ์ไม่เพิ่มขึ้น ทั้งที่เอกสารระบุไว้เป็นหนึ่งในวิธีแก้
ข้อค้นพบนี้**หนักแน่นขึ้น**จากการทดสอบข้ามชุดข้อมูล

### 5.3.4 สรุปผลการทดสอบข้ามชุดข้อมูลของหัวข้อ 5.3

| ข้อสรุปเบื้องต้น | ผลหลังทดสอบบนข้อมูลจากแบบจำลองจริง |
|---|---|
| ค่าที่เอกสารแนะนำสูงเกินจำเป็น (4.3.1) | **ถอนข้อสรุป** |
| คำเตือนปรากฏในกรณีที่ดีที่สุด (4.3.2) | **ลดระดับเป็นเอกสารไม่ครบถ้วน** |
| วิธีแก้ที่เอกสารระบุไม่เพียงพอ (4.3.3) | **ยืนยัน** |

ข้อสังเกตเชิงระเบียบวิธีที่ได้จากส่วนนี้คือ ข้อสรุปที่อธิบาย**กลไกการทำงานของระบบ**
สามารถยกไปใช้ข้ามชุดข้อมูลได้ ขณะที่ข้อสรุปที่ระบุ**ค่าเชิงปริมาณที่เหมาะสม**
ไม่สามารถยกไปใช้ข้ามชุดข้อมูลได้ ผู้อ่านควรใช้เส้นแบ่งนี้ในการตีความผลทุกส่วนของโครงงาน

## 5.4 ลักษณะของความล้มเหลวเป็นแบบขั้นบันได

**ตารางที่ 7** จุดเปลี่ยนของความผิดพลาด 3 รูปแบบ เปรียบเทียบสองชุดข้อมูล

| รูปแบบ | จุดเปลี่ยน (สังเคราะห์) | ผลหลังจุดเปลี่ยน | **จุดเปลี่ยน (ข้อมูลจริง)** | **ผลหลังจุดเปลี่ยน** |
|---|---|---|---|---|
| Q06 | k เกิน `ef_search` | ขอ 41 ได้ **40** | k เกิน 41 | ขอ 50 ได้ **41** |
| Q03 | เงื่อนไขกรอง 20% ถึง 2% | ขอ 10 ได้ **0** | เงื่อนไขกรอง 20% ถึง 0.5% | ขอ 10 ได้ **0** |
| L02 | แถวที่ถูกลบ 40% ถึง 50% | ขอ 10 ได้ **0** | แถวที่ถูกลบ 80% ถึง 90% | ขอ 10 ได้ **5** |

**ลักษณะเพดานตายตัวของ Q06 ยืนยันได้ทั้งสองชุดข้อมูล** กล่าวคือเมื่อขอเกินเพดานแล้ว
จะได้จำนวนเท่าเดิมเสมอไม่ว่าจะขอเพิ่มอีกเท่าใด (บนข้อมูลจริงขอ 50 ขอ 100 และขอ 1,000
ได้ 41 รายการเท่ากันทั้งหมด) ค่าเพดานต่างกันหนึ่งหน่วยระหว่างสองชุดข้อมูล

**ลักษณะขั้นบันไดของ Q03 ยืนยันได้เช่นกัน** แต่ตำแหน่งจุดเปลี่ยนต่างกัน

**ส่วน L02 ลักษณะขั้นบันไดไม่ปรากฏบนข้อมูลจริง** บนข้อมูลสังเคราะห์ผลลัพธ์เปลี่ยนจาก
ครบถ้วนเป็นศูนย์ภายในขั้นเดียว แต่บนข้อมูลจริงยังได้ผลครบจนถึงระดับแถวที่ถูกลบร้อยละ 80
และไม่เคยลดลงถึงศูนย์เลย ผู้พัฒนาจึงถอนข้อสรุปเรื่องลักษณะขั้นบันไดของ L02
และคงไว้เฉพาะ Q06 กับ Q03

ข้อค้นพบนี้มีนัยสำคัญต่อการออกแบบระบบเฝ้าระวัง เนื่องจากระบบที่ทำงานแบบกำหนด
ค่าขีดแบ่งไม่สามารถจับความล้มเหลวที่เปลี่ยนแบบขั้นบันไดได้ทัน

**Q03 และ L02 มีกลไกเดียวกันทุกประการ** ต่างกันที่ตัวกรอง ในกรณี Q03 ตัวกรองคือ
เงื่อนไข `WHERE` ที่ผู้พัฒนาเขียนเอง จึงมองเห็นได้จากโค้ด ส่วน L02 ตัวกรองคือกลไก
ควบคุมความสอดคล้องของข้อมูล (MVCC) ที่คัดแถวซึ่งถูกลบแล้วออก **ซึ่งไม่ปรากฏ
ในคำสั่งใด ๆ เลย** คำสั่งที่ให้ผลลัพธ์ผิดจึงมีหน้าตาเหมือนคำสั่งที่ถูกต้องทุกตัวอักษร

## 5.5 ผลตอบคำถามของโครงงานข้อที่ 3

ทดสอบกับแบบจำลองภาษาขนาดใหญ่ระดับแนวหน้า 2 ตัว รวม 3 การเก็บข้อมูล
โดยตัวแรกเก็บซ้ำ 2 รอบด้วยโจทย์ชุดเดิม

**ตารางที่ 8** ผลการทดสอบโค้ดที่สร้างโดยปัญญาประดิษฐ์

| การเก็บข้อมูล | ติดกับดัก | โจทย์ที่**ไม่ได้ใช้ดัชนีเวกเตอร์เลย** |
|---|---|---|
| แบบจำลอง ก รอบที่ 1 | 5 จาก 10 | 0 |
| แบบจำลอง ก รอบที่ 2 (โจทย์เดิม) | 7 จาก 10 | 3 |
| แบบจำลอง ข | 10 จาก 10 | 8 |

ตัวเลขในตารางนี้เป็น**จำนวนโจทย์ที่พบอาการ** มิใช่อัตราการเกิดในงานจริง
ตามเหตุผลที่ระบุไว้ในหัวข้อ 4.8

### 5.5.1 การวัดเพียงครั้งเดียวไม่เสถียร

แบบจำลองเดียวกัน โจทย์ชุดเดียวกันทุกตัวอักษร เมื่อถามในบทสนทนาใหม่ให้ผล
**5 จาก 10 และ 7 จาก 10** ซึ่งต่างกัน 2 โจทย์

ผลข้อนี้มีนัยเชิงระเบียบวิธี เนื่องจากโครงงานนี้กำหนดให้การทดลองทุกรายการทำซ้ำ
อย่างน้อย 3 รอบ และกำหนดให้การสร้างดัชนีทำซ้ำ 5 รอบต่อเงื่อนไข แต่การทดสอบ
ในหัวข้อนี้เดิมทำเพียงครั้งเดียว **จึงเป็นรายการเดียวในการศึกษาที่ไม่เป็นไปตามข้อกำหนด
ของตนเอง** และเมื่อทำซ้ำก็พบความไม่คงที่ในลักษณะเดียวกับที่ความผิดพลาด I04 แสดงไว้
กล่าวคือค่าที่ดูเสถียรเพียงพอที่จะรายงานได้ กลับเปลี่ยนไปเมื่อวัดซ้ำ

ตัวอย่างที่ชัดเจนคือโจทย์ที่ให้ตรวจสอบคุณภาพข้อมูล รอบแรกแบบจำลองเรียกใช้ฟังก์ชัน
ที่มีอยู่จริงและได้ผลถูกต้อง ส่วนรอบที่สองเรียกใช้ฟังก์ชันซึ่งไม่รองรับชนิดข้อมูลที่ใช้
ทำให้คำสั่งทำงานไม่สำเร็จ

### 5.5.2 รูปแบบ "เขียนจนดัชนีถูกปิด" ปรากฏในแบบจำลองทั้งสองตัว

ผลจากการเก็บข้อมูลสองครั้งแรกชี้ไปในทางที่ว่า แบบจำลอง ก ใช้ดัชนีได้ทุกโจทย์
ส่วนแบบจำลอง ข ไม่ใช้ดัชนีเลย ซึ่งอ่านได้โดยง่ายว่าเป็นลักษณะเฉพาะของแบบจำลอง

**การเก็บข้อมูลรอบที่สามหักล้างข้อสรุปดังกล่าว** แบบจำลอง ก ไม่ได้ใช้ดัชนีเวกเตอร์
ใน 3 โจทย์ ด้วยรูปแบบการเขียนแบบเดียวกับแบบจำลอง ข คือการนำเวกเตอร์ตั้งต้น
เข้ามาทางการเชื่อมตาราง (`JOIN`) หรือนิพจน์ตารางร่วม (CTE) แทนการเขียนเป็น
คำสั่งย่อยภายใน `ORDER BY` โดยตรง

คำสั่งทั้งสองรูปแบบให้ผลลัพธ์**ถูกต้องเท่ากันทุกรายการ** ต่างกันที่จำนวนบล็อกที่อ่าน
ประมาณ 20 เท่า ซึ่งเป็นกลไกเดียวกับความผิดพลาด Q02 และตรวจไม่พบหากไม่ตรวจ
แผนการทำงานของคำสั่ง

ข้อสรุปจึงเปลี่ยนจาก *ลักษณะเฉพาะของแบบจำลองหนึ่ง* เป็น **รูปแบบการเขียนที่
แบบจำลองภาษาเลือกใช้ร่วมกัน** ซึ่งเป็นข้อสรุปที่มีน้ำหนักมากกว่า และเป็นผลที่
เกิดขึ้นได้ก็ต่อเมื่อมีการเก็บข้อมูลซ้ำเท่านั้น

### 5.5.3 ความล้มเหลวสองรูปแบบที่ต่างกันคนละขั้ว

| | แบบจำลอง ก | แบบจำลอง ข |
|---|---|---|
| ผลลัพธ์ | ไม่ครบถ้วนบ่อยครั้ง | ครบถ้วนถูกต้องทุกโจทย์ |
| ต้นทุนต่อคำสั่ง | ประมาณ 974 บล็อก | ประมาณ 20,049 บล็อก |
| ลักษณะความล้มเหลว | เร็วแต่ไม่ถูก | ถูกแต่ช้า |

**ทั้งสองรูปแบบเป็นความล้มเหลวเมื่อนำขึ้นระบบจริง แต่มีเพียงรูปแบบเดียวที่มองเห็นได้
จากการตรวจผลลัพธ์** ทีมที่ตรวจรับงานด้วยเกณฑ์ว่าผลลัพธ์ถูกต้องหรือไม่ จะให้แบบจำลอง ข
ผ่านทั้งหมด ส่วนทีมที่ตรวจด้วยเกณฑ์ความเร็วจะได้ข้อสรุปกลับกัน

อนึ่ง การไม่ใช้ดัชนีของแบบจำลอง ข ทำให้ไม่มีทางเกิดกับดักที่ต้องอาศัยดัชนีในเส้นทาง
การทำงาน เช่น Q03 และ Q06 ตัวเลขรายกับดักของแบบจำลองนี้จึงตีความตรงตัวไม่ได้

### 5.5.4 กรณีที่มีนัยสำคัญที่สุด

ในโจทย์ที่ระบุเงื่อนไขไว้อย่างชัดเจนว่าต้องได้ผลลัพธ์ครบทุกครั้งไม่ว่าจะกรองด้วยเงื่อนไขใด
แบบจำลองได้เขียนคำอธิบายกลไกของปัญหาไว้ในหมายเหตุของคำตอบเองอย่างถูกต้อง ว่าดัชนี
คืนรายการผู้เข้ารอบตามจำนวนที่กำหนดก่อน แล้วจึงกรองภายหลัง ทำให้หมวดที่มีข้อมูลน้อย
ได้ผลลัพธ์ไม่ครบ

จากนั้นได้ตั้งค่าพารามิเตอร์ครบทุกตัวที่เอกสารของ pgvector ระบุไว้ ผลที่ได้คือ
**ศูนย์รายการ** และเมื่อเพิ่มเฉพาะค่า `work_mem` โดยไม่แก้ไขสิ่งอื่นใด ผลลัพธ์กลับมา
ครบถ้วน

ข้อค้นพบนี้แสดงว่าสาเหตุไม่ได้อยู่ที่แบบจำลองไม่รู้จักปัญหา เนื่องจากแบบจำลอง
วินิจฉัยกลไกได้ถูกต้อง แต่อยู่ที่ **ความรู้ซึ่งแบบจำลองเรียนมาจากเอกสาร ขาดในจุด
เดียวกับที่เอกสารขาด** ผลข้อนี้จึงยืนยันข้อค้นพบในหัวข้อ 5.3.3 ด้วยหลักฐานคนละประเภท

### 5.5.5 กรณีที่แบบจำลองทำนายพฤติกรรมของตัวเลือกแผนผิด

ในอีกโจทย์หนึ่ง แบบจำลองระบุในหมายเหตุว่าเมื่อข้อมูลในหมวดมีน้อย ระบบจะเลือกใช้
การค้นแบบสมบูรณ์และให้ผลครบถ้วน จึงสร้างดัชนีแบบ B-tree บนคอลัมน์ที่ใช้กรอง

การวัดจริงพบว่าตัวเลือกแผนไม่ได้เลือกเช่นนั้น ยังคงใช้ดัชนีเวกเตอร์และนำเงื่อนไขกรอง
ไปใช้ภายหลัง ผลลัพธ์ที่ได้คือศูนย์รายการ

## 5.6 การวัดหักล้างสมมติฐานของผู้พัฒนาเอง

ชื่อและคำอธิบายสาเหตุที่ผู้พัฒนากำหนดไว้ตั้งแต่ขั้นวางแผน **ถูกการวัดหักล้าง 4 จาก 12 รูปแบบ**
และทุกครั้งตรวจพบด้วยกลุ่มควบคุม ไม่ใช่ด้วยผลการวัดหลัก

| รูปแบบ | สมมติฐานเดิม | สิ่งที่กลุ่มควบคุมพบ |
|---|---|---|
| Q02 | การใช้ `WHERE` แทน `ORDER BY` | คำสั่งที่มีทั้ง `WHERE`, `ORDER BY` และ `LIMIT` ใช้ดัชนีได้ปกติ สาเหตุที่แท้จริงคือการขาด `ORDER BY` หรือ `LIMIT` |
| I04 | ความสุ่มของ k-means ใน IVFFlat | HNSW ซึ่งไม่มี k-means ก็ให้ผลไม่คงที่เช่นกัน และการปิดการสร้างแบบขนานไม่ได้แก้ปัญหา |
| I02 | การสร้างดัชนีขณะข้อมูลน้อย | ข้อมูล 50 รายการให้ค่าเรียกคืนสมบูรณ์ ตัวแปรที่แท้จริงคือความเป็นตัวแทน |
| L02 | แถวที่ถูกลบทำให้ดัชนีบวมและค่าเรียกคืนลด | การปรับปรุงแถวทำให้ดัชนีบวมจาก 195 เป็น 202 MB แต่ค่าเรียกคืนไม่ลดลง |

ข้อสังเกตเชิงระเบียบวิธีจากผลส่วนนี้คือ หากวัดเฉพาะสิ่งที่ตั้งใจวัด จะสามารถยืนยัน
สมมติฐานที่ผิดได้อย่างสมบูรณ์ทุกครั้ง การมีกลุ่มควบคุมที่สร้างเงื่อนไขซึ่งควรทำให้เกิด
อาการโดยไม่ให้เกิดอาการ จึงเป็นสิ่งจำเป็น ไม่ใช่ทางเลือก

## 5.7 ความสัมพันธ์ระหว่างความผิดพลาด

ความผิดพลาดที่ศึกษาไม่ได้เป็นอิสระต่อกัน แต่เชื่อมโยงกันในลักษณะที่มีนัยสำคัญ

- ค่า recall@100 ของ Q01 ที่ต่ำมาก อธิบายได้ด้วยกลไกของ Q06 กล่าวคือ 40 หารด้วย 100
  เป็นเพดานสูงสุดที่เป็นไปได้ ไม่ใช่ตัวชี้วัดคุณภาพ
- นิพจน์ที่ใช้แก้ปัญหา Q03 บนระบบรุ่น 17 ขึ้นไป เป็นนิพจน์เดียวกับที่ทำให้ดัชนี
  ใช้งานไม่ได้ในความผิดพลาด Q02
- ผลของ I04 ที่ว่าการสร้างดัชนีใหม่ให้คำตอบไม่เหมือนเดิม เป็นข้อบังคับให้การทดลอง
  ของ I02 ต้องสร้างดัชนี 5 รอบต่อเงื่อนไข มิฉะนั้นจะแยกไม่ออกว่าความแตกต่างเกิดจาก
  เงื่อนไขหรือจากความไม่คงที่ของการสร้าง
- ค่า `probes` = 5 แก้ได้ทั้งความผิดพลาด Q04 และ I04 กล่าวคือ ค่าที่เพียงพอ
  ไม่เพียงยกค่าเรียกคืน แต่ทำให้ผลลัพธ์คงที่ด้วย

ของข้อมูลชุดนั้น ส่วนนี้ทดสอบข้อจำกัดดังกล่าวโดยตรง

ในรูปแบบที่ผูกกับการกระจายตัวของข้อมูล**

ผู้พัฒนาได้ทำนายเส้นแบ่งนี้ไว้**ก่อน**ดำเนินการทดสอบ 6 รูปแบบหลัง และผลออกมาตรงตาม
คำทำนายทั้งหมด จึงมิใช่การอธิบายผลย้อนหลัง

ข้อสรุปที่อธิบาย**กลไกการทำงานของตัวประมวลผลคำสั่งหรือโครงสร้างของดัชนี** เช่น
เพดานของ `ef_search` เงื่อนไขของ `work_mem` ความจุของหน่วยความจำสร้างดัชนี
และการที่ opclass ไม่ตรงกันทำให้ดัชนีถูกละเลย ล้วนยืนยันได้ทั้งสองชุดข้อมูล

ส่วนข้อสรุปที่ระบุ**ค่าที่เหมาะสมหรือขนาดของผลกระทบ** ไม่สามารถยกไปใช้กับข้อมูล
ชุดอื่นได้ แม้จะได้จากการวัดอย่างเป็นระบบก็ตาม

### 5.8.4 ข้อสรุปของผู้พัฒนาเองที่ถูกหักล้าง

การทดสอบนี้หักล้างข้อสรุปเบื้องต้นของโครงงาน 5 ข้อ

| ข้อสรุปเดิม | ผลบนข้อมูลจริง |
|---|---|
| ค่า `probes` ที่เอกสารแนะนำสูงเกินจำเป็น | เหมาะสมแล้ว ถอนข้อสรุป |
| คำเตือนของระบบปรากฏในกรณีที่ดีที่สุด | ปรากฏถูกกรณี ลดระดับเป็นเอกสารไม่ครบถ้วน |
| L02 มีลักษณะขั้นบันได | ไม่ปรากฏ ค่อย ๆ ลดลงและไม่ถึงศูนย์ |
| ค่า `probes` เท่ากับ 5 ทำให้ผลคงที่สมบูรณ์ | ยังมีคำค้นเปลี่ยนคำตอบร้อยละ 60.5 |
| ดัชนี HNSW ไม่คงที่พอ ๆ กับ IVFFlat | HNSW เปลี่ยนเพียงร้อยละ 3 ส่วน IVFFlat ร้อยละ 91.5 |

ข้อสุดท้ายมีนัยเพิ่มเติม เนื่องจากข้อสรุปเดิมในหัวข้อ 5.6 ใช้ข้อเท็จจริงที่ว่า
ดัชนี HNSW ซึ่งไม่ใช้การแบ่งกลุ่มแบบ k-means ก็ให้ผลไม่คงที่เช่นกัน เป็นหลักฐาน
ตัดสมมติฐานที่ว่าความไม่คงที่มาจากการแบ่งกลุ่ม เมื่อทดสอบบนข้อมูลจริงพบว่า
หลักฐานชิ้นนั้นไม่ปรากฏ **การหักล้างในหัวข้อ 5.6 จึงยืนยันได้เฉพาะกับข้อมูลสังเคราะห์**
และกลไกที่ทำให้ HNSW ไม่คงที่ยังไม่ทราบเช่นเดิม

ผู้พัฒนารายงานผลส่วนนี้ไว้ทั้งหมดโดยไม่ตัดออก เนื่องจากเป็นหลักฐานโดยตรงว่า
กระบวนการที่ออกแบบไว้สามารถหักล้างข้อสรุปของตนเองได้ ซึ่งเป็นคุณสมบัติที่จำเป็น
ของการวัดที่เชื่อถือได้

# บทที่ 6 สรุปผลการดำเนินงานและข้อเสนอแนะ

## 6.1 ข้อสรุป

โครงงานนี้ตอบคำถามของโครงงานทั้งสามข้อได้ครบถ้วน

**คำถามข้อที่ 1** การตั้งค่าดัชนี ANN ตามค่าตั้งต้นทำให้ผลลัพธ์ที่ควรได้สูญหายไป
ระหว่าง 14 ถึง 41 เปอร์เซ็นต์ในระดับค่าเฉลี่ย และทุกการตั้งค่าที่ทดสอบมีคำถาม
ที่ได้คำตอบถูกต้องศูนย์รายการ โดยไม่มีข้อผิดพลาดใดปรากฏ

**คำถามข้อที่ 2** ความผิดพลาด 11 จาก 12 รูปแบบตรวจจับล่วงหน้าได้ด้วยโปรแกรมอัตโนมัติ
โดย 5 รูปแบบตรวจได้จากข้อมูลระบบเพียงอย่างเดียว ซึ่งนำไปใช้ในกระบวนการตรวจสอบ
ก่อนนำโค้ดขึ้นระบบจริงได้ทันที

**คำถามข้อที่ 3** โค้ดที่สร้างโดยแบบจำลองภาษาระดับแนวหน้าปรากฏความล้มเหลวเงียบ
สองรูปแบบที่ต่างกันโดยสิ้นเชิง คือให้ผลเร็วแต่ไม่ครบถ้วน กับให้ผลครบถ้วนแต่ไม่ได้ใช้
ดัชนีเลย โดยรูปแบบหลังปรากฏในแบบจำลองทั้งสองตัวเมื่อเก็บข้อมูลซ้ำ จึงเป็นรูปแบบ
ที่ใช้ร่วมกันมิใช่ลักษณะเฉพาะของแบบจำลองใด

กรณีสำคัญที่สุดแสดงว่าปัญหาไม่ได้เกิดจากการที่แบบจำลองไม่รู้จักกลไก แต่เกิดจาก
ช่องว่างของเอกสารที่แบบจำลองเรียนรู้มา

ผลข้อนี้รายงานเป็นการจำแนกรูปแบบ มิใช่เป็นอัตรา เนื่องจากชุดโจทย์มิใช่ตัวอย่างสุ่ม
และการเก็บข้อมูลซ้ำแสดงให้เห็นว่าการวัดเพียงครั้งเดียวไม่เสถียร

**ผลที่อยู่นอกวัตถุประสงค์เดิมแต่มีนัยสำคัญ** คือการพบว่าเอกสารทางการของ pgvector
ไม่ครบถ้วนในประเด็นความเป็นตัวแทนของข้อมูลขณะสร้างดัชนี ทั้งนี้ข้อสรุปเบื้องต้น
ในส่วนนี้ 2 จาก 3 ข้อถูกหักล้างด้วยการทดสอบซ้ำบนข้อมูลจากแบบจำลองจริงของโครงงานเอง
ซึ่งผู้พัฒนาได้รายงานไว้ครบถ้วนในหัวข้อ 5.3

## 6.2 ปัญหา อุปสรรค และข้อจำกัด

1. **ทดลองบนเครื่องเดียวและการตั้งค่าเดียว** ค่าที่เกี่ยวกับเวลาจึงใช้เปรียบเทียบ
   ภายในงานนี้เท่านั้น โครงงานลดผลกระทบด้วยการใช้จำนวนบล็อกที่อ่านเป็นตัวชี้วัดหลัก
   ซึ่งเป็นค่าเชิงโครงสร้างที่ไม่ขึ้นกับฮาร์ดแวร์
2. **ข้อมูลหลักเป็นข้อมูลสังเคราะห์** ซึ่งจำเป็นต่อการมีเฉลยที่แน่นอน
   ข้อจำกัดนี้**ได้รับการตรวจสอบแล้วบางส่วน** โดยทำซ้ำการวัดหลักบนข้อมูล
   จากแบบจำลองจริง (หัวข้อ 5.3.2 และภาคผนวก) ผลคือข้อค้นพบเชิงกลไกยืนยันได้
   ทั้งสองชุด แต่**ขนาดของผลขึ้นกับชุดข้อมูลอย่างมีนัยสำคัญ** และข้อสรุปหนึ่งข้อ
   ของความผิดพลาด I02 ใช้ไม่ได้นอกข้อมูลสังเคราะห์ ซึ่งได้แก้ไขไว้แล้วในหัวข้อนั้น
   ตัวเลขเชิงปริมาณทุกตัวในเล่มนี้จึงต้องอ่านพร้อมกับชุดข้อมูลที่ใช้วัดเสมอ
3. **กลไกที่ทำให้การสร้างดัชนี HNSW ใหม่ให้ผลไม่เหมือนเดิมยังไม่ทราบ** โครงงาน
   ตัดสาเหตุที่เป็นไปได้ออกไป **สามประการ** คือ (ก) ฝั่งคำสั่งค้นหา ซึ่งพิสูจน์แล้วว่า
   ให้ผลตรงกันทุกครั้งเมื่อวัดซ้ำบนดัชนีตัวเดิม (ข) การสร้างดัชนีแบบขนาน ซึ่งเมื่อปิด
   แล้วผลยังไม่คงที่ และ (ค) ตัวสร้างเลขสุ่มของเซสชัน ซึ่งเมื่อกำหนดค่าเริ่มต้นเท่ากัน
   ทุกครั้งด้วยคำสั่ง `setseed` แล้วผลยังไม่คงที่เช่นกัน

   **ภายหลังผู้พัฒนาได้ตรวจสอบรหัสต้นฉบับของส่วนขยายและของระบบฐานข้อมูล
   แล้วพบว่ากลไกดังกล่าวเป็นข้อมูลสาธารณะอยู่แล้ว** กล่าวคือส่วนขยายกำหนดระดับชั้น
   ของแต่ละจุดในกราฟด้วยนิพจน์ที่อาศัยเลขสุ่ม ซึ่งเป็นขั้นตอนมาตรฐานของอัลกอริทึม
   HNSW [6] โครงสร้างกราฟจึงแตกต่างกันทุกครั้งที่สร้างดัชนีโดยการออกแบบ มิใช่ข้อบกพร่อง

   นอกจากนี้ยังพบว่าเลขสุ่มที่ส่วนขยายใช้มาจากตัวสร้างเลขสุ่มส่วนกลางของระบบฐานข้อมูล
   ขณะที่คำสั่ง `setseed` ควบคุมตัวสร้างเลขสุ่มคนละตัวซึ่งใช้กับฟังก์ชัน `random` เท่านั้น
   **การทดลองในข้อ (ค) จึงไม่มีทางให้ผลบวกได้ตั้งแต่ต้น** ผู้พัฒนารายงานข้อผิดพลาด
   เชิงระเบียบวิธีนี้ไว้ตามที่เกิดขึ้นจริง

   ผลที่ได้จากการตรวจสอบนี้มีคุณค่าในทางปฏิบัติมากกว่าข้อสรุปเดิม กล่าวคือ
   **ระบบที่ต้องการผลการค้นหาซึ่งทำซ้ำได้อย่างแน่นอน ไม่สามารถใช้ดัชนีแบบ HNSW
   ของส่วนขยายนี้ได้** เนื่องจากไม่มีช่องทางให้ผู้ใช้กำหนดค่าเริ่มต้นของตัวสร้างเลขสุ่ม
   ส่วนกลาง ทางเลือกที่เหลือคือใช้การค้นแบบสมบูรณ์ หรือคงดัชนีเดิมไว้โดยไม่สร้างใหม่
4. **ผลของคำถามข้อที่ 3 มาจากแบบจำลอง 2 ตัว รวม 3 การเก็บข้อมูล และชุดโจทย์
   ที่ผู้พัฒนาออกแบบเอง** จึงยืนยันได้ว่าปรากฏการณ์เกิดขึ้นจริงและเกิดซ้ำข้ามแบบจำลอง
   แต่**ระบุเป็นอัตราไม่ได้** เนื่องจากชุดโจทย์มุ่งไปยังกับดักที่ทราบล่วงหน้า
   มิใช่ตัวอย่างสุ่มจากงานพัฒนาจริง การเพิ่มจำนวนโจทย์ไม่ได้แก้ข้อจำกัดนี้
   เพราะข้อจำกัดอยู่ที่วิธีคัดเลือกโจทย์ มิใช่ที่ขนาดตัวอย่าง

   นอกจากนี้การเก็บข้อมูลซ้ำยังพบว่าการวัดเพียงครั้งเดียวให้ผลไม่คงที่
   การศึกษาที่จะขยายผลส่วนนี้จึงต้องเก็บข้อมูลอย่างน้อย 2 รอบต่อแบบจำลอง
5. **ความผิดพลาด 3 รูปแบบตรวจได้เฉพาะขณะเกิดเหตุ** เครื่องมือที่ตรวจครั้งเดียว
   ไม่สามารถจับได้

## 6.3 ความเชื่อถือได้ของเครื่องมือวัด

ระหว่างการพัฒนา พบข้อบกพร่องในเครื่องมือที่ผู้พัฒนาสร้างขึ้นเองจำนวน 32 รายการ
ซึ่งบันทึกไว้ทั้งหมด ในจำนวนนี้มี 2 กรณีที่ตัวตรวจจับรายงานว่าไม่พบปัญหา
ทั้งที่ความผิดพลาดเกิดขึ้นอยู่จริง

ทั้งสองกรณีถูกตรวจพบด้วยข้อกำหนดในกระบวนการที่แยกคำถามว่า *ความผิดพลาดเกิดขึ้น
จริงหรือไม่* ออกจากคำถามว่า *ตัวตรวจจับใช้การได้หรือไม่* และบังคับให้พิสูจน์อย่างหลัง
แยกต่างหาก

การบันทึกข้อบกพร่องเหล่านี้ไว้อย่างครบถ้วนเป็นส่วนหนึ่งของการรายงานความเชื่อถือได้
ของเครื่องมือวัด ซึ่งจำเป็นต่อการประเมินน้ำหนักของผลของโครงงาน

## 6.4 ข้อเสนอแนะสำหรับการนำไปใช้

1. **ตรวจสอบ operator class ของดัชนีให้ตรงกับ operator ที่โปรแกรมใช้** เป็นการตรวจ
   ที่ทำได้ทันทีจากข้อมูลระบบ และป้องกันความผิดพลาดที่ทำให้ดัชนีไม่ถูกใช้เลย
2. **วัดค่าเรียกคืนกับข้อมูลของตนเองก่อนกำหนดค่าพารามิเตอร์** ไม่ควรใช้ค่าตั้งต้น
   หรือสูตรจากเอกสารโดยไม่ตรวจสอบ
3. **รายงานคุณภาพรายคำถามควบคู่กับค่าเฉลี่ย** เนื่องจากค่าเฉลี่ยปกปิดกรณีที่รุนแรง
4. **วัดค่าเรียกคืนใหม่ทุกครั้งหลังสร้างดัชนีใหม่** เนื่องจากการสร้างดัชนีไม่ให้ผลเหมือนเดิม
5. **แยกสถานะตรวจไม่ได้ออกจากสถานะไม่พบปัญหา** ในเครื่องมือตรวจสอบทุกชนิด

## 6.5 แนวทางการพัฒนาต่อ

1. **ขยายการทดสอบคำถามข้อที่ 3 ไปยังแบบจำลองอื่น** เพื่อแยกว่าเป็นลักษณะร่วม
   ของแบบจำลองภาษาโดยทั่วไป หรือเป็นลักษณะเฉพาะของแบบจำลองที่ทดสอบ
   ชุดโจทย์และเครื่องมือให้คะแนนพร้อมใช้แล้ว
2. **ขยายการทดสอบบนข้อมูลจากแบบจำลองจริงให้ครอบคลุมทุกความผิดพลาด**
   โครงงานนี้ได้ทดสอบแล้วสองรายการคือ Q01 และ I02 (หัวข้อ 5.3.2)
   รายการที่เหลือยังไม่ได้ตรวจสอบข้ามชุดข้อมูล และควรใช้แบบจำลองสร้าง
   เวกเตอร์มากกว่าหนึ่งตัว เนื่องจากผลที่ได้แสดงว่าขนาดของผลขึ้นกับชุดข้อมูลมาก
3. **แยกกลไกที่ทำให้การสร้างดัชนี HNSW ไม่ให้ผลคงที่**
4. **ขยายเครื่องมือตรวจจับให้ครอบคลุมความผิดพลาดที่ต้องเฝ้าขณะเกิดเหตุ**

## ภาคผนวก ค บันทึกการตัดสินใจและความผิดพลาดระหว่างการทำโครงงาน

```bash
docker compose up -d
python scripts/audit.py                 # ตรวจความครบถ้วน 33 หัวข้อ
python scripts/audit.py --reproduce     # รันโปรแกรมฉีดซ้ำ 9 รูปแบบ
python scripts/quietfail_check.py --dsn "postgresql://..."   # ตรวจฐานข้อมูลอื่น
```

## ภาคผนวก จ ชุดโจทย์สำหรับทดสอบโค้ดที่สร้างโดยปัญญาประดิษฐ์

โจทย์ 10 ข้อพร้อมเกณฑ์การให้คะแนน อยู่ในโฟลเดอร์ `rq3/`

## ภาคผนวก ฉ คู่มือการติดตั้ง

**สิ่งที่ต้องมี** Docker Desktop · Python 3.12 ขึ้นไป · Git

```bash
git clone https://github.com/Earthkodyai/quietfail
cd quietfail
docker compose up -d
```

โหลดข้อมูลและเฉลย ทำครั้งแรกครั้งเดียว ตามลำดับ

```bash
docker compose exec -T db psql -U lab -d faultlab -f /sql/qf10_vector_schema.sql
docker compose exec -T db psql -U lab -d faultlab -f /sql/qf11_query_set.sql
docker compose exec -T db psql -U lab -d faultlab -v rows=100000 -f /sql/qf12_seed_corpus.sql
docker compose exec -T db psql -U lab -d faultlab -f /sql/qf13_recall.sql
```

ตรวจว่าติดตั้งสมบูรณ์

```bash
python scripts/audit.py
```

ผลลัพธ์ต้องลงท้ายว่า *ผ่านครบทุกข้อ* ถ้าไม่ผ่าน รายงานจะระบุว่าข้อใดและเพราะเหตุใด
ผู้ใช้ระบบปฏิบัติการวินโดวส์ให้ใช้ PowerShell ตามหมายเหตุใน `WINDOWS.md` ของคลังซอร์ส

## ภาคผนวก ช คู่มือการใช้งาน

**ฉีดความผิดพลาดหนึ่งรูปแบบแล้วดูผล** ตัวอย่างรูปแบบ Q06

```bash
docker compose exec -T db psql -U lab -d faultlab -f /sql/q06_limit_exceeds_ef.sql
```

ตัวฉีดทุกตัวมีเงื่อนไขตรวจสอบภายใน ถ้าความผิดพลาดไม่เกิดตามที่ตั้งใจ สคริปต์จะหยุด
พร้อมข้อความแจ้งเหตุ

**ถามสถานะระบบว่ามีความผิดพลาดใดอยู่**

```bash
docker compose exec -T db psql -U lab -d faultlab -f /sql/score.sql
```

คำตอบต่อข้อคือ `DETECTED` หรือ `NOT_DETECTED` หรือ `CANNOT_CHECK`
โดยข้อสุดท้าย**ไม่นับว่าผ่าน**

**ตรวจฐานข้อมูลอื่นที่ไม่ใช่ของโครงงานนี้** ซึ่งเป็นของส่งมอบหลัก

```bash
python scripts/quietfail_check.py --dsn "postgresql://user:pass@host/db" --max-limit 100
```

| รหัสจบ | ความหมาย |
|---|---|
| 0 | ตรวจครบ ไม่พบปัญหา |
| 1 | พบปัญหา ควรหยุดกระบวนการนำขึ้นระบบ |
| 2 | ไม่พบปัญหา แต่มีข้อที่ตรวจไม่ได้ |

เงื่อนไขของฐานข้อมูลปลายทาง มิฉะนั้นจะได้รหัสจบ 2 คือต้องเปิด `pg_stat_statements`
ผ่าน `shared_preload_libraries` และดัชนีแบบ ivfflat ต้องระบุค่า `lists` ตอนสร้าง

การรันซ้ำการทดลองทั้งหมดดูภาคผนวก ง

⭐ ข้อสังเกตเชิงโครงสร้าง — เอกสารจัดกลุ่ม Q03 · L02 · Q06 ไว้ประโยคเดียวกัน
------------------------------------------------------------------------------

  FAQ "Why are there less results for a query after adding an HNSW index?"

    "Results are limited by the size of the dynamic candidate list
     (hnsw.ef_search), which is 40 by default.        <- Q06
     There may be even less results due to dead tuples <- L02
     or filtering conditions in the query.             <- Q03
     Enabling iterative index scans can help address this."   <- ทางแก้ร่วม

  **สาม fault ที่โครงงานนี้แยกเป็นคนละข้อ เอกสารรวมไว้ในประโยคเดียว
    และให้ทางแก้ตัวเดียวกัน** ซึ่งตรงกับที่การวัดของเราเพิ่งยืนยัน (E43 · E44)
    ว่า iterative_scan แก้ได้ทั้งสามข้อ

  -> **สนับสนุนข้ออ้าง "L02 กลไกเดียวกับ Q03" ที่เขียนไว้ตั้งแต่ต้น**
     และเพิ่ม Q06 เข้าไปในกลุ่มเดียวกันด้วย
     การแยกเป็น 3 ข้อยังมีประโยชน์ (อาการและวิธีตรวจจับต่างกัน)
     แต่ต้องระบุให้ชัดว่ากลไกร่วมกัน ไม่ใช่สามเรื่องอิสระ


==============================================================================
🔴 A. Q04 — แถว probes สูง ไม่ได้ใช้ index เลย · ไม่เคยตรวจ plan
==============================================================================

เอกสารเขียนเตือนไว้ตรงๆ ในหัวข้อ IVFFlat Query Options

  "A higher value provides better recall at the cost of speed, and it can be
   set to the number of lists for exact nearest neighbor search
   (**at which point the planner won't use the index**)"

`sql/q04_default_params.sql` **ไม่เคยตรวจ plan สักครั้ง** จึงไม่มีทางรู้

------------------------------------------------------------------------------
วัดจริง — lists = 100 · ขอ 10 แถว · ตรวจจากชื่อ index ใน plan
------------------------------------------------------------------------------

  qf_real (384 มิติ)                 qf_real2 (768 มิติ)
  probes  ใช้ index   buffers        probes  ใช้ index   buffers
  ------  ---------  --------        ------  ---------  --------
       1     t            349             1     t            815
      10     t          2,386            10     t          5,630
      20     t          5,004            20     t         11,167
      30     t          6,938            30     t         16,736
      40     t          9,172            40     t         21,234
      50     t         11,049        **  50     f        601,594  **
  **  100     f         23,550  **       100     f        601,594

  384 มิติ : ทิ้ง index ที่ probes = 100
  768 มิติ : ทิ้ง index ที่ probes = **50**  <- เร็วกว่า และ**ก่อนถึง lists**

------------------------------------------------------------------------------
ข้ออ้างที่ต้องแก้
------------------------------------------------------------------------------

  1. ตาราง Q04 แถว `probes=100 (ทุกกลุ่ม) · 11,146 ms`
     -> **ไม่ใช่เวลาของ IVFFlat** เป็นเวลาของ exact search ที่ planner เลือกเอง
        recall 1.0000 ถูกต้องในแง่สิ่งที่ผู้ใช้ได้ **แต่ไม่ใช่ผลของการจูน probes**

  2. 🔴 ข้ออ้าง 768 มิติ: *"ค่าที่พอเลื่อนอีก — probes=50 ได้ 1.0000
     (384 ต้องถึง 100)"*
     -> **ทั้งสองจุดคือจุดที่ planner ทิ้ง index พอดี**
        สิ่งที่วัดได้จริงไม่ใช่ "ค่า probes ที่ทำให้ recall เต็ม"
        แต่คือ **"ค่า probes ที่ planner เลิกใช้ index"** ซึ่งคนละเรื่องกัน

  3. assertion ข้อ 4 ใน `q04_default_params.sql`
     ("probes=100 ต้องช้ากว่า probes=1") **ผ่าน แต่วัดผิดสิ่ง** —
     เป็นการเทียบ IVFFlat scan กับ Seq Scan ไม่ใช่การเทียบ probes สองค่า

------------------------------------------------------------------------------
✅ สิ่งที่ยังยืน และไม่กระทบเลย
------------------------------------------------------------------------------

  ข้อสรุปหลักของ Q04 อยู่ที่ **ปลายล่าง** ของตาราง ซึ่งใช้ index ทุกแถว

     probes=1 (ค่าเริ่มต้น) -> recall 0.6607 · แย่สุดต่อ query 0.0000
     probes=10 (เอกสารแนะนำ) -> 0.9527

  ทั้งสองแถวยืนยันแล้วว่าใช้ index จริง -> **"ค่าเริ่มต้นไม่พอ" ไม่กระทบ**

------------------------------------------------------------------------------
⭐ และมันเชื่อมกับข้อค้นพบเดิมของ Q03 ที่ 768 มิติ
------------------------------------------------------------------------------

  Q03 บน 768 มิติเคยพบว่า *"planner เลิกใช้ index เอง เพราะ index ใหญ่เท่าตัว"*
  ตอนนี้เห็นอาการเดียวกันใน Q04 -> **เป็นปรากฏการณ์ร่วม ไม่ใช่เรื่องเฉพาะ Q03**

  **ขนาดของ index เปลี่ยนว่า planner จะใช้มันไหม ซึ่งเปลี่ยนว่า
    "สิ่งที่เรากำลังวัด" คืออะไร โดยไม่มีอะไรแจ้ง**

  ที่ 768 มิติ probes=50 buffers กระโดดจาก 21,234 -> 601,594 (28 เท่า)
  ซึ่งเป็นต้นทุนของ Seq Scan บนคอลัมน์ที่ถูก TOAST (ตรงกับกับดักข้อ 6ก)

🔴 B. L02 — "REINDEX คือคนมักแก้ผิด" ขัดกับเอกสาร และวัดแล้วกลับหัว
==============================================================================

`FAULTS.md` จัด `REINDEX` ไว้ในช่อง **"คนมักแก้ผิด"** พร้อมวงเล็บว่า
*"แพงกว่า VACUUM มากโดยไม่จำเป็น"*

**แต่เอกสารแนะนำ REINDEX ตรงๆ** ในหัวข้อ Performance > Vacuuming

  "Vacuuming can take a while for HNSW indexes.
   **Speed it up by reindexing first.**
       REINDEX INDEX CONCURRENTLY index_name;
       VACUUM table_name;"

และ **repo นี้ไม่เคยวัด REINDEX สักครั้ง** (ค้นทั้ง results/ และ sql/ = 0 ครั้ง)
จึงเป็นข้ออ้างเชิงปริมาณที่ไม่มีหลักฐาน — ละเมิดกฎเหล็กข้อ 2 ของตัวเอง

------------------------------------------------------------------------------
วัดจริง — ตารางสภาพเดียวกันเป๊ะ · 100,000 แถว · ตาย 90% · ไม่ autovacuum
------------------------------------------------------------------------------

  วิธี                  เวลา      index หลัง    ได้/10
  -------------------  -------   ----------   ------
  (ก่อนแก้)                 —      195.3 MB        0
  **REINDEX**          **3.4 วิ**  **19.5 MB**     10
  **VACUUM**          **12.8 วิ**   195.3 MB      10
  VACUUM หลัง REINDEX    0.4 วิ     19.5 MB       10

------------------------------------------------------------------------------
ข้อสรุปที่ต้องแก้ — กลับหัวทั้งสองด้าน
------------------------------------------------------------------------------

  ❌ เคยเขียน : "REINDEX แพงกว่า VACUUM มากโดยไม่จำเป็น"
  ✅ วัดได้   : REINDEX **เร็วกว่า 3.8 เท่า** และ **ลดขนาด index 10 เท่า**
                (195.3 -> 19.5 MB) ขณะที่ VACUUM ไม่ลดเลย

  เหตุผลเชิงกลไกชัดเจน — REINDEX สร้างกราฟใหม่จากแถวที่ยังมีชีวิต 10,000 แถว
  ส่วน VACUUM ต้องไล่ทั้ง index 195 MB เพื่อตามเก็บรายการที่ตาย
  **ยิ่งตายเยอะ REINDEX ยิ่งได้เปรียบ** ซึ่งคือเหตุผลที่เอกสารแนะนำไว้

  ⚠️ ข้อแม้ที่ยังต้องเขียนไว้ — `REINDEX` ธรรมดา**ล็อกตาราง**
     เอกสารจึงเขียนว่า `REINDEX INDEX CONCURRENTLY`
     ข้อได้เปรียบเรื่องเวลาจึงไม่ได้แปลว่าใช้แทนกันได้ทุกสถานการณ์

  🔴 และตัวเลข "VACUUM 27 วินาที" ที่เคยบันทึกไว้ วัดคนละเงื่อนไข
     (mwm 64MB) รอบนี้วัดที่ 256MB ได้ 12.8 วินาที
     **เทียบข้ามเงื่อนไขไม่ได้** — ตัวเลขในตารางข้างบนวัดคู่กันในรอบเดียว

  ✅ **ข้อสรุปหลักของโครงงานไม่กระทบ** — ทั้งสองข้อเป็นรายละเอียดรอบนอก
     "ค่าเริ่มต้นไม่พอ และล้มเหลวโดยไม่มี error" ยังยืนทุกประการ
     และแถวที่ใช้พิสูจน์ข้อนั้นยืนยันแล้วว่าใช้ index จริง

  ⭐ **ได้ของใหม่ 2 อย่าง**
     1. เอกสารรวม Q03 · L02 · Q06 ไว้ประโยคเดียว ทางแก้เดียว
        -> สนับสนุนข้ออ้าง "กลไกเดียวกัน" ด้วยหลักฐานจากเอกสาร
     2. planner ทิ้ง index ตามขนาด index -> เกิดทั้ง Q03 และ Q04
        -> "สิ่งที่เรากำลังวัด" เปลี่ยนได้เองโดยไม่มีอะไรแจ้ง

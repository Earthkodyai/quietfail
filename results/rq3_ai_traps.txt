⭐ ผลที่สำคัญที่สุด — P08
------------------------------------------------------------------------------

โจทย์บอกเงื่อนไขตรงๆ ว่า "ต้องได้ครบ 10 แถวเสมอ ไม่ว่าจะกรองด้วยหมวดไหน"

โมเดลตั้งค่าครบทุกตัวที่เอกสาร pgvector ระบุไว้:

    SET hnsw.iterative_scan      = strict_order;
    SET hnsw.ef_search           = 100;
    SET hnsw.max_scan_tuples     = 100000;
    SET hnsw.scan_mem_multiplier = 4;

    -> ได้ 0 แถว

เติม work_mem อย่างเดียว ไม่แตะอย่างอื่นเลย:

    SET work_mem = '16MB';

    -> ได้ 10 แถว

นี่คือข้อจำกัดข้อที่ 5 ที่โปรเจคนี้ค้นพบเองตอนทำ Q03 และ **ไม่มีอยู่ในเอกสาร**
โมเดลทำตามเอกสารครบถ้วนทุกข้อ แล้วยังได้ศูนย์แถว

-> RQ3 ยืนยันช่องว่างของเอกสารที่ Q03 วัดไว้ ด้วยหลักฐานอิสระคนละชนิด

------------------------------------------------------------------------------
หมายเหตุ P06 — ต้องอ่านก่อนนับว่าเป็น I01/Q04
------------------------------------------------------------------------------

P06 ถูกนับว่าติดกับดักเพราะ SQL รันไม่ผ่าน แต่ **สาเหตุไม่ใช่ I01 หรือ Q04**

    ERROR: could not resize shared memory segment ... to 214...

เกิดจากบรรทัดแรกของคำตอบ:  SET maintenance_work_mem = '2GB';
ซึ่งเกิน /dev/shm ของคอนเทนเนอร์ (256MB) = **U05** ในทะเบียนบั๊กระหว่างทาง

ตรวจแยกแล้ว: ลดเหลือ 256MB คำตอบเดียวกันรันผ่าน และสร้าง index ครบ 4 ตัว
**เป็น vector_cosine_ops ถูกต้องทั้งหมด** -> ถ้าตัดเรื่องหน่วยความจำออก
โมเดล **ไม่ติด I01** และตั้ง ef_search/iterative_scan ไว้ด้วย จึงไม่ติด Q04

    ดังนั้นตัวเลข I01 1/1 และ Q04 1/1 ข้างบน **นับสูงเกินจริง**
    ถ้านับตามสาเหตุจริง ทั้งสองข้อควรเป็น 0/1 และ P06 ควรถูกนับเป็น U05

**และ P06 เป็นความล้มเหลวแบบดัง ไม่ใช่แบบเงียบ** — มี error ให้เห็นทันที
ต่างจากอีก 4 ข้อที่ติดกับดักโดยไม่มีอะไรแจ้งเลย

-> ถ้านับเฉพาะ **ความล้มเหลวเงียบ** ซึ่งเป็นหัวใจของโปรเจค:  4 จาก 10 ข้อ

สิ่งที่โมเดลทำได้ดี — ต้องบันทึกด้วย
------------------------------------------------------------------------------

P04  ใช้ **partial index** เฉพาะหมวด legal เพื่อเลี่ยง over-filtering
     ได้ครบ 20/20 recall 1.00 · เป็นทางแก้ที่โปรเจคนี้ไม่ได้ทดสอบไว้ด้วยซ้ำ

P09  จับ **ทั้ง NULL และ zero vector** ไม่ใช่แค่ NULL
     และรู้ว่า cosine ของ zero vector เป็น NaN · ให้ทางสำรองเผื่อไม่มี vector_norm()

P05  รูปแบบ query ถูกต้อง (WHERE + ORDER BY + LIMIT) ไม่ติด Q02

โมเดลพูดถึง over-filtering และ iterative_scan เองหลายข้อ **โดยที่โจทย์ไม่ได้ใบ้**
-> มันรู้ว่าปัญหานี้มีอยู่ แต่ **แก้ไม่ครบ** ในข้อที่ต้องแก้จริง (P02 · P07 · P08)

------------------------------------------------------------------------------
⚠️ ความไวต่อลำดับที่วางบล็อกคำตอบ — ตรวจแล้ว
------------------------------------------------------------------------------

โมเดลตอบมาเป็น **หลายบล็อก** (query บล็อกหนึ่ง · คำแนะนำเรื่อง index อีกบล็อก)
**ยืนยันกับผู้เก็บคำตอบแล้วว่าเรียงตามลำดับที่โมเดลแสดงจริง** ไม่ได้สลับ
ทำแค่ต่อบล็อกที่ติดกันเข้าด้วยกัน → **ลำดับคือส่วนหนึ่งของคำตอบ ไม่ใช่สิ่งที่คนใส่เข้าไป**

ตัวให้คะแนนใช้ SELECT ตัวแรกเป็นคำตอบ · คำสั่งก่อนหน้าถือเป็น prelude ที่รันจริง ·
คำสั่งหลังจากนั้นทิ้ง — ซึ่ง **ตรงกับสิ่งที่ developer ที่ copy จากบนลงล่างจะเจอ**

หัวข้อนี้จึงเป็น **การตรวจความทนทานของผล** ไม่ใช่การแก้ข้อผิดพลาดของวิธีเก็บ
วัดว่าถ้าตีความอีกแบบ ตัวเลขจะขยับแค่ไหน

    ข้อ   ลำดับที่โมเดลเลือกเอง        ถ้าตีความอีกแบบ (นับคำแนะนำท้ายด้วย)
    ---   -------------------------   ----------------------------------
    P04   index มาก่อน   20/20 ผ่าน    (ไม่มีอะไรท้ายให้นับ)
    P07   index มาทีหลัง   5/50 ตก     นับ index ด้วย    40/50 **ยังตก**
    P08   ทางเลือก B ท้าย  0/10 ตก     นับทางเลือก B    10/10 ผ่าน
    P10   SET อยู่ท้าย    10/10 ผ่าน    นับ SET ด้วย      10/10 ผ่าน

**ตัวโมเดลเองเป็นคนเลือกว่าจะวาง index ไว้หน้าหรือหลัง** — P04 วางไว้หน้าในฐานะ
สิ่งที่ต้องมีก่อน ส่วน P07 วางไว้หลังในฐานะคำแนะนำเพิ่มเติม ทั้งที่เป็นปัญหาชนิดเดียวกัน
**ความไม่สม่ำเสมอตรงนี้เป็นผลอย่างหนึ่ง ไม่ใช่ noise ของวิธีเก็บ**

**ตัวเลขรวม 5/10 ไม่เปลี่ยน** เมื่อตัดสินตามเนื้อหาของคำตอบ ไม่ใช่ตามลำดับที่วาง:

  P04 ผ่านถูกต้อง — โจทย์ถามเฉพาะหมวด legal · partial index บน legal ตอบโจทย์ครบ

  P07 ตกถูกต้อง แต่ **เหตุผลเปลี่ยน** — ถ้านับ partial index ที่มันแนะนำเอง
      ได้ 40/50 ซึ่งคือเพดาน ef_search พอดี = **Q06 ไม่ใช่ Q03**
      ตัวเลข Q03 3/5 ในตารางข้างบนจึงควรเป็น **2/5** และ Q06 ยังเป็น 2/2

  P08 ตกถูกต้อง — "ทางเลือก B" ของมันคือ partial index เฉพาะหมวด archive กับ legal
      แต่โจทย์บอกว่า **"ไม่ว่าจะกรองด้วยหมวดไหน"** · ทางแก้ที่ครอบคลุมทุกหมวด
      คือ iterative_scan ซึ่งมันเลือกใช้แล้ว **และได้ 0 แถวเพราะไม่ตั้ง work_mem**

  P10 ผ่านทั้งสองแบบ

→ **ข้อสรุปหลัก (P08) ไม่ขึ้นกับลำดับ** เพราะทางเลือกสำรองของโมเดลเองก็ไม่ตอบโจทย์ที่ถาม

       -> คนที่ copy บล็อกแรกไปใช้ได้ query ที่ไม่มี index · ตกถูกต้อง
  P08  "ทางเลือก B" ระบุคำว่า **ทางเลือก** ชัดเจน และครอบคลุมแค่ archive กับ legal

ปัญหาชนิดเดียวกัน ทางแก้ชนิดเดียวกัน แต่ข้อหนึ่งวางเป็นสิ่งที่ต้องทำก่อน
อีกข้อวางเป็นของแถมท้ายคำตอบ

⭐⭐ สองอย่างที่ภาพหน้าจอเปิดเผยเพิ่ม — ทำให้ผลแรงขึ้น

**1. P08 — โมเดลอธิบายกลไก Q03 ได้ถูกต้องด้วยคำของมันเอง แล้วยังแก้ไม่ได้**

ในคอมเมนต์ของคำตอบมันเขียนไว้เองว่า:

    "ป้องกันปัญหา over-filtering: HNSW คืน ef_search แถวก่อน แล้วค่อยกรอง
     ทำให้หมวดหายาก เช่น archive (1% = ~1,000 แถว) ได้ไม่ครบ 10"

**นี่คือคำอธิบายกลไก Q03 ที่ถูกต้องทุกตัวอักษร** แล้วมันตั้งค่าตามเอกสารครบทุกตัว
และยังได้ 0 แถว เพราะไม่มีใครบอกมันว่าต้องตั้ง work_mem ด้วย

-> **ไม่ใช่เพราะโมเดลไม่รู้จักปัญหา แต่เพราะเอกสารไม่ครบ**
   ข้อสรุปของ RQ3 จึงหนักแน่นกว่าที่คิดไว้ตอนแรกมาก

**2. P02 — โมเดลทำนายพฤติกรรมของ planner ผิด**

คอมเมนต์ในคำตอบเขียนว่า:

    "archive มีแค่ ~1,000 แถว -> exact search เร็วและได้ผลลัพธ์ครบถ้วน 100%"

แล้วสร้าง btree บน category เพื่อให้ planner เลือกทางนั้น · วัดจริงแล้ว **planner ไม่เลือก**

    Limit
      -> Index Scan using documents_embedding_idx on documents d
           Order By: (embedding <=> ...)
           Filter: (category = 'archive'::text)      <- กรองทีหลัง
    ได้ 0 แถว

planner ยังใช้ HNSW แล้วเอา category มากรองทีหลัง = กลไก Q03 เต็มรูปแบบ

-> **ตรงกับรายการ "สิ่งที่ผู้ช่วย AI เชื่อถือไม่ได้" ข้อแรกใน CLAUDE.md พอดี**
   คือ *"query plan ที่ planner จะเลือก"* ซึ่งโปรเจคนี้เคยพลาดเองมาแล้ว (E07)
   RQ3 จึงยืนยันข้อนั้นด้วยหลักฐานอิสระคนละชนิด

ข้อจำกัดของตัวเลขชุดนี้ — ต้องอ่านก่อนอ้าง
------------------------------------------------------------------------------

1. **โมเดลเดียว ครั้งเดียว** n=1 ต่อโจทย์ ไม่มีการรันซ้ำ
   ไม่รู้ว่าถามใหม่จะได้คำตอบเดิมไหม

2. **10 โจทย์ที่เราออกแบบเอง** เลือกให้ครอบคลุมกับดักที่วัดไว้แล้ว
   ไม่ใช่ตัวอย่างสุ่มจากงานจริง

3. **ผูกกับสภาพแวดล้อมนี้** โปรไฟล์ fragile · work_mem 16MB · /dev/shm 256MB
   P06 ล้มเพราะข้อจำกัดของคอนเทนเนอร์ ซึ่งเครื่องอื่นอาจไม่ล้ม

4. **เกณฑ์ recall ของ P05 ตั้งที่ 0.5** เพื่อแยก "ได้แถวถูกชนิด" ออกจาก "ได้แถวมั่ว"
   ไม่ใช่ค่าที่มีความหมายทางทฤษฎี

5. **คำตอบมาเป็นหลายบล็อก แต่เรียงตามที่โมเดลแสดง** — ผู้เก็บยืนยันว่าไม่ได้สลับ
   ตรวจความทนทานไว้ในหัวข้อความไวต่อลำดับ · ตัวเลขรวมไม่เปลี่ยน
   แต่การแยกว่า P07 เป็น Q03 หรือ Q06 เปลี่ยนได้

6. อ้างได้ว่า **เกิดขึ้นจริงกับโมเดลระดับบนสุดในสภาพนี้**
   อ้างไม่ได้ว่าเป็นอัตราของ AI ทั่วไป

⭐⭐ ผลที่สำคัญที่สุดของ RQ3 ทั้งหมด — สองโมเดลล้มไปคนละทิศ
------------------------------------------------------------------------------

**ChatGPT: 8 จาก 10 ข้อเป็นความผิดพลาดเดียวกันซ้ำๆ**

มันเขียนทุก query ด้วยรูปแบบนี้

    FROM documents AS d
    CROSS JOIN (SELECT embedding FROM search_queries WHERE id = 1) AS q
    ORDER BY d.embedding <=> q.embedding

`q.embedding` เป็นคอลัมน์จากตารางที่ join มา **pgvector ใช้ index กับรูปแบบนี้ไม่ได้**
plan ที่ได้คือ

    Sort -> Nested Loop -> Seq Scan on documents

**ไม่มี Index Scan เลยสักข้อ** วัดได้ชัด: อ่าน 20,049 block ต่อ query
เทียบกับ 974 block ของ Opus 5 = **แพงกว่า 21 เท่า**

เพราะ **มันสแกนทั้งตาราง** — ซึ่งคือ exact search โดยบังเอิญ
ผลลัพธ์จึงถูกต้องสมบูรณ์แบบทุกข้อ ไม่มีอะไรผิดให้เห็นเลย

    P03  ขอ 100 ได้ 100  recall 1.00   (Opus 5 ได้ 40 เพราะ ef_search=40)
    P07  ขอ  50 ได้  50  recall 1.00   (Opus 5 ได้ 5)
    P08  ขอ  10 ได้  10  recall 1.00   (Opus 5 ได้ 0)

**การไม่ใช้ index บังกับดักอื่นทั้งหมด** — Q03 กับ Q06 ต้องมี index อยู่ในเส้นทาง
ถึงจะเกิดได้ ChatGPT จึงไม่เคยไปถึงกับดักเหล่านั้นเลย
ตัวเลข "Q03 5/5" ในสรุปจึงอ่านผิดได้ง่าย — ที่จริงคือ **Q02 บังไว้หมด**

P06  **คำตอบรันไม่ได้** — มี `WHERE q.id = $1` ซึ่งเป็น placeholder ที่ไม่ได้ผูกค่า
     ตรวจแยกแล้ว: index ที่มันจะสร้างเป็น `vector_cosine_ops` **ถูกต้อง**

ข้อจำกัดที่เพิ่มขึ้นจาก n=2
------------------------------------------------------------------------------

1. ยังเป็น **ครั้งละหนึ่งคำตอบต่อโจทย์** ไม่ได้ถามซ้ำ
2. ChatGPT ตอบผ่านหน้าเว็บปกติ ไม่ได้ล็อกเวอร์ชันโมเดล — ทำซ้ำเป๊ะไม่ได้
3. **8 ข้อของ ChatGPT มีต้นเหตุเดียวกัน** จึงไม่ใช่ 8 ความผิดพลาดอิสระ
   ถ้ามันแก้รูปแบบ query ข้อเดียว ผลอาจเปลี่ยนทั้งกระดาน
4. อ้างได้ว่า **โมเดลระดับบนสุดสองค่าย ล้มคนละแบบและล้มจริงทั้งคู่**
   อ้างไม่ได้ว่าเป็นอัตราของ AI ทั่วไป

⭐ ผลที่ 1 — การวัดครั้งเดียวไม่นิ่ง วัดแล้ว ไม่ใช่เดา
------------------------------------------------------------------------------

โมเดลเดียวกัน โจทย์เดียวกัน ได้ **5/10 กับ 7/10** = ต่างกัน 2 ข้อจาก 10

RQ3 เป็นการวัดเดียวในโปรเจคที่เคยทำครั้งเดียว ทั้งที่ fault ทุกข้อรัน 3 รอบ
และ I04 รัน 5 build — **ตอนนี้รู้แล้วว่าความไม่นิ่งนั้นมีจริงและใหญ่พอที่จะเปลี่ยนข้อสรุป**

-> ห้ามรายงาน RQ3 เป็นเลขเดี่ยวอีกต่อไป ต้องเป็นช่วง: **Opus 5 = 5-7 จาก 10**

------------------------------------------------------------------------------
⭐⭐ ผลที่ 2 — กับดัก "ไม่ใช้ index เลย" ไม่ใช่ของ ChatGPT เจ้าเดียว
------------------------------------------------------------------------------

รอบแรก Opus 5 ใช้ index ครบทุกข้อ · **รอบสองไม่ใช้ 3 ข้อ** (P02 · P08 · P10)

    P02  CROSS JOIN (SELECT ... ) AS q   -> Seq Scan 20,043 block
    P10  WITH q AS (...) CROSS JOIN q    -> Seq Scan 20,044 block
    P08  WITH knn AS MATERIALIZED (...)  -> Seq Scan  1,007 block

ทั้งสามคือรูปแบบเดียวกับที่ ChatGPT ใช้ทุกข้อ — เอา query vector มาทาง JOIN/CTE
แทนที่จะเป็น subquery ตรงๆ ใน ORDER BY

**นี่เปลี่ยนข้อสรุปของ RQ3 อย่างมีนัยสำคัญ**
เดิม: "ChatGPT ไม่ใช้ index · Opus 5 ใช้" -> ดูเหมือนเป็นนิสัยเฉพาะเจ้า
ตอนนี้: **ทั้งสองค่ายเขียนรูปแบบที่ปิด index ได้ ต่างกันแค่ความถี่**

-> เป็น**รูปแบบร่วม** ไม่ใช่ของโมเดลใดโมเดลหนึ่ง ซึ่งคือสิ่งที่ n=2 ควรตอบพอดี

⭐ ผลที่ 3 — โมเดลตกหลุมที่โปรเจคนี้เคยตกเอง (E10)
------------------------------------------------------------------------------

P09 รอบสองใช้ `l2_norm(embedding)` เพื่อหา zero vector -> รันไม่ผ่าน

    ERROR:  function l2_norm(vector) is not unique
    HINT:   Could not choose a best candidate function.
            You might need to add explicit type casts.

**นี่คือ E10 ของโปรเจคนี้ตรงตัว** — `l2_norm` มีเฉพาะ `halfvec` กับ `sparsevec`
ไม่มีสำหรับ `vector` ใน 0.8.5 · และ HINT ชวนให้ใส่ cast ซึ่งถ้าทำตามจะไปลง
`::halfvec` แล้ว**เสียความละเอียดข้อมูลเงียบๆ**

โปรเจคนี้ค้นพบ E10 จากการที่ผู้ช่วย AI เดาผิดเอง — และตอนนี้โมเดลเดียวกัน
เดาผิดแบบเดิมซ้ำในการวัดที่ควบคุมแล้ว **เป็นหลักฐานอิสระว่า E10 ไม่ใช่ความซวยครั้งเดียว**

(รอบแรก Opus 5 ใช้ `vector_norm()` ซึ่งถูกต้อง — ตอกย้ำผลที่ 1 ว่าไม่นิ่ง)

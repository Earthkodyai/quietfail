ข้อมูล    : qf_corpus (สังเคราะห์ 100,000 แถว) — เลือกเพราะสัญญาณแรงสุด
วิธี      : 3 build ต่อเงื่อนไข · ปิด parallel build · ef_search=40 · k=10
            เทียบคำตอบ top-10 แบบเซ็ต (H32)

     เงื่อนไข      | query ทั้งหมด | เปลี่ยนคำตอบ |  %

 A setseed เท่ากัน |         200 |        101 | 50.5

==============================================================================
🔴 ผล — setseed **ไม่ได้** ทำให้ build ซ้ำได้
==============================================================================

  เงื่อนไข              query ที่เปลี่ยนคำตอบ (จาก 200)
  A  setseed(0.42) ทุก build      101  (50.5%)
  B  ไม่ setseed เลย              117  (58.5%)

**ถ้า PRNG ของ session เป็นกลไก A ต้องได้ 0** — ได้ 101 จึงตัดออกได้

------------------------------------------------------------------------------
⚠️ ห้ามอ่านว่า "setseed ช่วยลดจาก 117 เหลือ 101"
------------------------------------------------------------------------------

**ค่าฐานเองก็แกว่งข้ามรอบ** — I04 เดิมวัด HNSW ef=40 ได้ **132/200** (2026-07-27)
รอบนี้ค่าฐานได้ **117/200** ทั้งที่เงื่อนไขเดียวกันทุกประการ

  ค่าฐานที่วัดได้จนถึงตอนนี้   117 · 132     (ช่วง 15)
  A ได้                       101           (ต่ำกว่าค่าฐานต่ำสุด 16)

ส่วนต่าง A-B = 16 **อยู่ในระดับเดียวกับที่ค่าฐานแกว่งเอง** และมีเงื่อนไขละ 1 รอบ
จึงบอกไม่ได้ว่าเป็นผลจริงหรือ noise · **ต้องเก็บหลายรอบต่อเงื่อนไขถึงจะตอบได้**

ที่พูดได้อย่างเดียวคือ: **setseed ไม่ได้ทำให้ผลนิ่ง**

------------------------------------------------------------------------------
สิ่งที่ตัดออกได้เพิ่ม — ตอนนี้เป็น 3 สาเหตุ
------------------------------------------------------------------------------

  1. ฝั่ง query        วัดซ้ำบน index ตัวเดิม -> ตรงกันทุก query        (กลุ่มควบคุม ก)
  2. parallel build   ปิดแล้วยังแกว่ง 127/200                          (กลุ่มควบคุม ค)
  3. **PRNG ของ session**  setseed ค่าเดิม -> ยังแกว่ง 101/200         (รอบนี้)

**ข้อ 3 มีน้ำหนักเพราะปิด parallel build ไว้ด้วย** จึงไม่ใช่กรณีที่ worker
มี PRNG แยกแล้ว setseed ไปไม่ถึง — ทุกอย่างอยู่ใน session เดียวที่ setseed แล้ว

------------------------------------------------------------------------------
เหลืออะไรให้คนทำต่อ
------------------------------------------------------------------------------

การสุ่มที่ทำให้กราฟต่างกัน **ไม่ได้มาจาก PRNG ที่ `setseed()` ควบคุม**
ผู้ที่จะทำต่อควรดูที่:

  - pgvector อาจใช้ตัวสุ่มของตัวเอง แยกจาก PRNG ของ session
  - ลำดับการอ่านหน้า (page) ระหว่าง build ซึ่งขึ้นกับสภาพ buffer cache
  - โครงสร้างภายในของ graph ที่ขึ้นกับลำดับการแทรก

**ต้องอ่านซอร์สของ pgvector ถึงจะตอบได้** ซึ่งอยู่นอกขอบเขตของโครงงานนี้
แต่ตอนนี้คำถามแคบลงมากแล้ว และมีหลักฐานว่าอะไร*ไม่ใช่*ครบ 3 ข้อ

------------------------------------------------------------------------------
บั๊กของสคริปต์ที่เจอระหว่างรัน
------------------------------------------------------------------------------

  ERROR: record variable cannot be part of multiple-item INTO list

plpgsql ไม่ยอมให้ตัวแปรชนิด record อยู่ใน `INTO` ร่วมกับตัวแปรอื่น
ทำให้ assertion ท้ายไฟล์ไม่ได้รัน · **ตรวจด้วยมือแล้วว่า qf_corpus fingerprint เดิม
(5a32cba5...) 100,000 แถว และไม่มี vector index ค้าง** · แก้สคริปต์แล้ว

==============================================================================
🔴 แก้ข้อสรุปข้างบน — อ่านซอร์สแล้วพบว่าการทดลองนี้เล็งผิดตัว (2026-07-31)
==============================================================================

หลังรันเสร็จจึงไปอ่านซอร์สของ pgvector และ PostgreSQL พบว่า
**setseed() ไม่มีทางมีผลต่อการสร้าง HNSW ตั้งแต่แรก** เพราะเป็น PRNG คนละตัว

  pgvector src/hnsw.h
      #define RandomDouble() pg_prng_double(&pg_global_prng_state)

  pgvector src/hnswutils.c  (HnswInitElement)
      int level = (int) (-log(RandomDouble()) * ml);

  PostgreSQL src/backend/utils/adt/pseudorandomfuncs.c  (random() และ setseed())
      static pg_prng_state prng_state;      <- file-local คนละตัวกับ global

**setseed() คุม `prng_state` ซึ่งเป็น static ในไฟล์ของ SQL random()
ส่วน HNSW ใช้ `pg_global_prng_state` — คนละตัวกันสิ้นเชิง**

------------------------------------------------------------------------------
ข้อสรุปที่ถูกต้อง
------------------------------------------------------------------------------

**กลไกของ I04 ทราบแล้ว และเป็นข้อมูลสาธารณะมาตลอด**

HNSW สุ่ม "ระดับชั้น" ให้ทุกจุดตอน build ด้วยสูตร -log(uniform) * ml
ซึ่งเป็นอัลกอริทึมมาตรฐานของ HNSW (Malkov & Yashunin) ไม่ใช่เรื่องเฉพาะของ pgvector
กราฟที่ได้จึงต่างกันทุก build โดยการออกแบบ

**สิ่งที่การทดลองนี้ยืนยันได้จริง (แม้จะเล็งผิด):**
ตั้ง seed จาก SQL ไม่ช่วย — ซึ่งตอนนี้อธิบายได้แล้วว่าเพราะอะไร
และแปลว่า **ไม่มีวิธีทำให้ HNSW build ซ้ำได้จากฝั่ง SQL เลย**
เพราะ pg_global_prng_state ไม่มีอินเทอร์เฟซให้ผู้ใช้ตั้งค่า

------------------------------------------------------------------------------
ข้อควรรู้เชิงระเบียบวิธี
------------------------------------------------------------------------------

**กฎเหล็กข้อ 1 บอกให้เอกสารและซอร์สเป็นคนตัดสิน — รอบนี้ทำสลับลำดับ**
คือออกแบบการทดลองก่อน แล้วค่อยไปอ่านซอร์ส ทั้งที่ซอร์สเปิดสาธารณะและตอบได้ใน 3 บรรทัด

กลุ่มควบคุม ก/ข/ค ที่ทำไว้ก่อนหน้า**ไม่เสียเปล่า** เพราะเป็นตัวยืนยันว่าปรากฏการณ์
มีจริงและวัดได้ · โดยเฉพาะกลุ่ม ข (HNSW ไม่มี k-means แต่ก็แกว่ง) ซึ่ง**ซอร์สยืนยันให้**
ว่าถูกต้อง — HNSW มีการสุ่มของตัวเองแยกจาก k-means ของ IVFFlat

F01 — connection หมดเพราะ transaction ค้าง
==============================================================================

✅ **ตัวเลข 17 slot ยืนยันแล้วจากค่าจริงในระบบ**

  max_connections                 = 20
  superuser_reserved_connections  = 3     (boot_val 3)
  reserved_connections            = 0     (boot_val 0 · GUC ใหม่ตั้งแต่ PG16)
  -> role ธรรมดาได้ 20 - 3 - 0 = **17 slot**  ตรงกับที่ทะเบียนเขียนไว้

  ⚠️ ข้อควรรู้ที่ทะเบียนยังไม่ได้เขียน — PG16 เพิ่ม `reserved_connections`
     แยกจาก `superuser_reserved_connections` ถ้าใครตั้งค่านี้ ตัวเลข 17 จะเลื่อน
     บนโปรไฟล์ของ repo เป็น 0 จึงไม่กระทบ

✅ ข้อความ error ตรงกับที่แก้ไว้ใน E13 แล้ว

⚠️ **ช่องว่างในทะเบียน** — ตาราง F01 ไม่มีแถว "ทางแก้ที่ถูก" ทั้งที่ fault อื่นมี
   และเอกสารมีคำตอบตรงตัวอยู่แล้ว

     idle_in_transaction_session_timeout:
       "Terminate any session that has been idle ... within an open transaction
        for longer than the specified amount of time ... This option can be used
        to ensure that idle sessions do not hold locks for an unreasonable
        amount of time."

   ค่าปริยาย = **0 (ปิด)**  ·  ตัวฉีด `faults/f01_idle_in_transaction.sh:130`
   พูดถึงอยู่แล้ว แต่ทะเบียนไม่ได้บันทึก -> เติมแล้ว


==============================================================================
🔴 F03 — เอกสารมีตัวแยกให้ และเราไม่เคยพูดถึงมันเลย
==============================================================================

F03 อ้างว่าเป็น "ข้อที่พิสูจน์วิทยานิพนธ์ของโปรเจคทั้งหมด" เพราะ F03 กับ F03b
**ให้ข้อความ error เหมือนกันเป๊ะแต่คนละสาเหตุ**

`lock_timeout` **ไม่เคยถูกกล่าวถึงในทะเบียน F03 เลยสักครั้ง**
(ค้นทั้ง FAULTS.md · REPORT.md · CLAUDE.md · EVIDENCE.md · เล่ม = 0 ครั้ง)

------------------------------------------------------------------------------
สิ่งที่เอกสารเขียนไว้ตรงตัว
------------------------------------------------------------------------------

  lock_timeout:
    "Abort any statement that waits longer than the specified amount of time
     while attempting to acquire a lock on a table, index, row, or other
     database object.
     **Unlike statement_timeout, this timeout can only occur while waiting
     for locks.**
     Note that if statement_timeout is nonzero, it is rather pointless to set
     lock_timeout to the same or larger value, since the statement timeout
     would always trigger first."

  -> เป็นพารามิเตอร์ที่ออกแบบมาเพื่อ **แยกการรอ lock ออกจากการทำงานช้า** โดยตรง
     ซึ่งคือเส้นแบ่ง F03 / F03b พอดี

------------------------------------------------------------------------------
วัดจริง — orders 200,000 แถว · session A ถือ row lock ของ id=1
------------------------------------------------------------------------------

  เงื่อนไข                                        ข้อความ error ที่ได้
  --------------------------------------------  -------------------------------
  F03  · lock_timeout = 0 (ค่าปริยาย)             canceling statement due to
       statement_timeout = 2s                     **statement timeout**

  F03  · lock_timeout = 500ms                     canceling statement due to
       statement_timeout = 2s                     **lock timeout**       <- ต่างแล้ว

  F03b · lock_timeout = 50ms                      canceling statement due to
       statement_timeout = 100ms                  **statement timeout**

  **ตั้ง lock_timeout แล้ว สองกรณีให้ข้อความคนละอย่างทันที**
  แยกได้จากข้อความล้วนๆ ไม่ต้องใช้ pg_blocking_pids() เลย

------------------------------------------------------------------------------
ข้ออ้างที่ต้องแก้ และรูปแบบที่ถูกต้อง
------------------------------------------------------------------------------

  ❌ เคยเขียน : "F03 กับ F03b ให้ข้อความ error เหมือนกันเป๊ะ แยกไม่ออกจากข้อความ"

  ✅ ที่ถูก   : "**ภายใต้ค่าเริ่มต้น** (`lock_timeout = 0` ซึ่งเป็นค่าปริยาย)
                ข้อความเหมือนกันเป๊ะ แยกไม่ออก
                PostgreSQL **มีตัวแยกให้แล้ว** คือ `lock_timeout`
                แต่ **ปิดไว้โดยปริยาย** จึงไม่มีใครได้ประโยชน์จากมันจนกว่าจะตั้งเอง"

------------------------------------------------------------------------------
⭐ และรูปแบบที่ถูกต้องนี้ **แข็งกว่าเดิม** เพราะไปตรงกับ Q06 พอดี
------------------------------------------------------------------------------

                     กลไกที่ช่วยได้        ค่าปริยาย    ผลที่ตามมา
  -----------------  --------------------  ---------  ----------------------
  Q06 (pgvector)     hnsw.iterative_scan   **off**    ผลขาดเงียบๆ
  F03 (PostgreSQL)   lock_timeout          **0**      วินิจฉัยผิดเงียบๆ

  **ทั้งสองระบบมีเครื่องมือที่แก้ปัญหาได้อยู่แล้ว แต่ปิดไว้โดยปริยาย**
  -> ข้อสรุปหลักของโครงงานที่ว่า "ค่าเริ่มต้นคือปัญหา" ครอบคลุมทั้งสองฝั่ง
     ไม่ใช่แค่ฝั่ง pgvector อย่างที่เคยเขียน

  🔴 นี่คือครั้งที่ห้าของรูปแบบ "ไม่ได้ลองสิ่งที่เอกสารมีให้"
     (E42 · E43 x2 · E44 · รอบนี้)

F05 — คิว lock
==============================================================================

✅ **ตารางความขัดแย้งของ lock ตรงกับเอกสารทุกตัว**

  ACCESS EXCLUSIVE : "Conflicts with locks of all modes ... Many forms of
                     ALTER INDEX and ALTER TABLE also acquire a lock at
                     this level."
  ACCESS SHARE     : "Conflicts with the ACCESS EXCLUSIVE lock mode only.
                     The SELECT command acquires a lock of this mode."
  SHARE            : "Acquired by CREATE INDEX (without CONCURRENTLY)."   <- I03

⚠️ **แต่พฤติกรรมของ "คิว" ที่เป็นหัวใจของ F05 ไม่ปรากฏในเอกสาร**

  ข้ออ้างของ F05 คือ *ALTER TABLE ที่ยังไม่ได้เริ่มทำงาน แค่รออยู่ในคิว
  ก็ทำให้ SELECT ที่มาทีหลังค้างไปด้วย*

  ค้นด้วยตัวเองในหน้าเต็มของ explicit-locking · mvcc-intro · sql-altertable
  · sql-createindex แล้ว **ไม่พบประโยคใดที่ระบุว่าผู้รอ lock บล็อกผู้ที่มาทีหลัง**
  เอกสารให้แค่ตารางความขัดแย้งแบบคู่ต่อคู่ ซึ่งอนุมานผลของคิวไม่ได้โดยตรง

  -> **F05 จึงเป็นข้อที่สองต่อจาก I04 ที่เอกสารเงียบ** และพิสูจน์ด้วยการรันเอง
     (ยืนยันแล้ว 3 จังหวะ · `granted=false` 2 แถว)

  📌 ระบุให้ถูก: "เอกสารให้ตารางความขัดแย้ง **แต่ไม่ได้อธิบายผลของการเข้าคิว**"
     ไม่ใช่ "เอกสารไม่พูดถึง lock เลย"

✅ ทางแก้ที่ตัวฉีดเสนอ (`lock_timeout` ให้ DDL) ตรงกับเอกสาร

F10 — สถิติเก่า planner เลือกผิด
==============================================================================

✅ `default_statistics_target` = **100** ทั้ง setting และ boot_val (ยืนยันจากระบบ)
   -> ข้ออ้าง "MCV เก็บได้ 100 ค่า คงที่ตาม default_statistics_target" ถูกต้อง

✅ ข้ออ้างว่า `n_distinct` เป็นค่าประมาณที่เปลี่ยนทุกครั้งที่ ANALYZE
   ตรงกับที่เอกสารอธิบายเรื่องการสุ่มตัวอย่างของ ANALYZE
   (วัดเองได้ 4,656 / 4,679 / 4,695 บนข้อมูลชุดเดิม)

✅ ไม่พบข้ออ้างใดของ F10 ที่ขัดกับเอกสาร

สรุปรวมทั้งโครงงาน — ตรวจครบ 16 fault แล้ว
==============================================================================

  ฝั่ง pgvector (E45)   12 ข้อ -> 10 ตรง · 2 ผิด (Q04 · L02)
  ฝั่ง PostgreSQL       4 ข้อ  ->  3 ตรง · 1 ต้องผ่อน (F03)

  **ข้อที่เอกสารเงียบจริง มี 2 ข้อ** — I04 (build ซ้ำไม่ได้) · F05 (พฤติกรรมคิว)
  ทั้งคู่พิสูจน์ด้วยการรันเอง ไม่ได้อ้างเอกสาร

  **ไม่มีข้อใดที่พิสูจน์ได้ว่าเอกสารเขียนผิด** — ที่เจอทั้งหมดคือ
  เราไม่ได้อ่านให้ครบ หรือไม่ได้ลองสิ่งที่เอกสารมีให้

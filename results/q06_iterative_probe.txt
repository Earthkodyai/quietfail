ข้อสรุป
==============================================================================

1. 🔴 **รายการทางแก้ของ Q06 ไม่ครบ — ต้องเพิ่ม `iterative_scan`**

   ทะเบียนเดิมเขียนว่าทางแก้คือเพิ่ม `ef_search` และไม่เคยกล่าวถึง
   `iterative_scan` เลย · เป็นความผิดพลาดชนิดเดียวกับ L02 ใน E43
   คือ **ไม่ได้ทดสอบปุ่มที่เอกสารมีให้**

   `relaxed_order + mult=32` ได้ recall **0.9397** ที่ 1,715 buffers
   เทียบกับทางแก้เดิม `ef=100` ได้ 0.9244 ที่ 1,594 buffers
   -> **ทั้งสองทางใช้ได้จริง อยู่ในระดับเดียวกัน** ไม่มีทางไหนเหนือกว่าชัดเจน

2. ⭐ **แต่ผลรอบนี้ทำให้ข้อสรุปหลักของ Q06 แข็งขึ้น ไม่ใช่อ่อนลง**

   `iterative_scan` แก้ **จำนวนแถว** ได้สมบูรณ์ (40 -> 100 ครบทั้ง 200 query)
   แต่ recall ยังได้แค่ **0.7572** ที่หน่วยความจำค่าเริ่มต้น

   ```
   ได้ครบ 100 แถวทั้ง 200 query   แต่ 1 ใน 4 ของแถวเป็นของผิด
   ```

   -> **"ได้ครบ" กับ "ได้ถูก" เป็นคนละเรื่อง และปุ่มคนละตัวคุม**
      ซึ่งคือข้อสรุปหลักของ Q06 อยู่แล้ว ("แก้ Q06 ไม่ได้แก้ Q01")
      ตอนนี้มีหลักฐานตรงกว่าเดิมมาก เพราะเห็นทั้งสองตัวเลขในตารางเดียวกัน

   **และเป็นกับดักที่อันตรายกว่าเดิมด้วย** — ทีมที่เปิด `iterative_scan`
   แล้วเห็นจำนวนแถวกลับมาครบ จะเชื่อว่าแก้ปัญหาได้แล้ว
   ทั้งที่ recall ยังขาดไป 24% และ **ไม่มี error ใดๆ เหมือนเดิม**

3. ✅ **แย่สุดต่อ query = 0.0000 ทุกเงื่อนไข รวมทั้ง ef=200**

   ยืนยันผลเดิมของโครงงาน — ไม่มีการตั้งค่าใดในตารางนี้ที่ทำให้ทุก query
   ได้ผลถูกอย่างน้อยหนึ่งอัน · ข้อนี้ไม่ถูกกระทบเลย

4. ⚠️ **ต้องผ่อนข้ออ้าง "Q06 เป็นของ pgvector เฉพาะตัว"**

   เดิมอ้างว่าเจ้าอื่น (Milvus · Weaviate · OpenSearch) ป้องกันไว้ให้แล้ว
   ส่วน pgvector ไม่ได้ป้องกัน · **ที่ถูกคือ pgvector มีกลไกป้องกันตั้งแต่ 0.8.0
   แต่ตั้งค่าปริยายเป็นปิด** ซึ่งเป็นคำอธิบายที่แคบกว่าและตรงกว่า

   ข้อนี้ไม่กระทบข้อสรุปเรื่องค่าเริ่มต้น เพราะค่าเริ่มต้นยังคงเป็น `off` จริง

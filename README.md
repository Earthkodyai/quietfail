# QuietFail

**ชุดทดสอบความล้มเหลวเงียบของระบบค้นหาแบบเวกเตอร์บน PostgreSQL**

> ใส่ index ให้ vector search แล้วเร็วขึ้นหลายสิบเท่า
> แต่ผลลัพธ์ที่ควรเจอหายไปส่วนหนึ่ง **โดยไม่มี error ใดๆ แจ้ง**
> QuietFail วัดว่าหายไปเท่าไหร่ ด้วยเฉลยที่เถียงไม่ได้

```
สถานะ: ชุด fault ครบทั้ง 12 ข้อแล้ว · fault ที่มีตัวฉีด + ตัวตรวจ = 15 ข้อ
        ตรวจความพร้อมทั้ง repo 33 หัวข้อ ผ่านหมด
```

📄 **รายงานฉบับเต็มอยู่ที่ [`REPORT.md`](REPORT.md)** — ผล · อภิปราย ·
ภัยคุกคามต่อความสมเหตุสมผล · งานต่อ · README นี้เป็นฉบับย่อ

## ตัวเลขหลัก

384 มิติ · 200 query · cosine · **ไม่ได้จูนอะไรเลย** (`ef_search=40` · `probes=1` ตามค่าเริ่มต้น)

**ที่ 100,000 แถว**

| | recall@10 | recall@100 | แย่สุด@10 | เร็วขึ้น |
|---|---|---|---|---|
| exact (ไม่มี index) | **1.0000** | **1.0000** | 1.0000 | 1.0× |
| HNSW ค่าเริ่มต้น | 0.8565 | 0.3903 | **0.0000** | 32.6× |
| IVFFlat ค่าเริ่มต้น | 0.7870 | 0.7793 | **0.0000** | 44.6× |

**ที่ 500,000 แถว — พารามิเตอร์เดิมทุกตัว**

| | recall@10 | recall@100 | แย่สุด@10 | ครบ 10/10 | เร็วขึ้น |
|---|---|---|---|---|---|
| exact (ไม่มี index) | **1.0000** | **1.0000** | 1.0000 | 200/200 | 1.0× |
| HNSW ค่าเริ่มต้น | **0.5885** | 0.3871 | **0.0000** | **2/200** | **117.1×** |
| IVFFlat ค่าเริ่มต้น | 0.7820 | 0.7857 | **0.0000** | 108/200 | 51.6× |

> ที่ 500,000 แถว HNSW **เร็วขึ้น 117 เท่า** แต่คืนคำตอบที่ถูกต้องครบ
> **แค่ 2 จาก 200 query** — ไม่มี error ไม่มี warning ผลลัพธ์ทุกแถวดูสมเหตุสมผล

### ผลที่สำคัญที่สุด: index สองแบบเสื่อมตามขนาดข้อมูลคนละแบบ

| | 100k → 500k |
|---|---|
| **HNSW** recall@10 | 0.8565 → **0.5885** (ตกลง 31%) |
| IVFFlat recall@10 | 0.7870 → 0.7820 (แทบไม่ขยับ) |

สาเหตุอยู่ที่**รูปแบบของค่าเริ่มต้น** ไม่ใช่คุณภาพของ algorithm:

- `ef_search = 40` เป็น **ค่าสัมบูรณ์** → ข้อมูลโต 5 เท่า สัดส่วนที่ค้นจริงหดลง 5 เท่า
- `probes = 1` จาก `lists = 100` เป็น **ค่าสัมพัทธ์** → คงที่ 1% ไม่ว่าข้อมูลจะโตแค่ไหน

**และ HNSW เร็วขึ้นพร้อมกับที่มันพังลง** (32.6× → 117.1×)
ทีมที่เฝ้าดูแต่ latency จะเห็นว่าระบบ "ดีขึ้นเรื่อยๆ" ตอนข้อมูลโต

หลักฐาน: `results/q01_recall_collapse_100k.txt` · `results/q01_recall_collapse_500k.txt`

### แล้วมันเป็นบั๊กของ pgvector หรือเปล่า

รัน Q01 ซ้ำบน **Qdrant 1.12.4** ด้วย corpus / ชุด query / เฉลย / สูตร **ชุดเดียวกันทั้งหมด**
ตัวแปรเดียวที่ต่างคือ engine

| engine (สองแถวแรกตั้ง ef เท่ากัน) | recall@10 | recall@100 |
|---|---|---|
| pgvector HNSW `ef_search=40` | 0.8565 | **0.3903** |
| Qdrant HNSW `hnsw_ef=40` | 0.9945 | **0.9895** |

**ไม่ใช่บั๊กของ pgvector** — Qdrant ก็เสีย recall เหมือนกัน (แย่สุดต่อ query 0.90 ·
ที่ k=100 ได้ครบแค่ 69 จาก 200 query) การค้นแบบประมาณทำผลลัพธ์หายจริงทั้งคู่

**แต่ก็ไม่ใช่ว่าทุกตัวพังเท่ากัน** — ขนาดของความเสียหายถูกกำหนดโดย
ค่าเริ่มต้นที่ผู้พัฒนาเลือก และโดยพฤติกรรมเมื่อ `ef < k`
pgvector ปล่อยให้ `ef_search=40` ตัดคุณภาพของ `LIMIT 100` ทิ้ง · Qdrant ไม่ปล่อย

หลักฐาน: `results/q01_qdrant_cross_engine.txt`

### ชั้น 3 — จับคู่กับเครื่องมืออื่นจากเอกสารทางการ

**ทบทวนเอกสาร ไม่ใช่ผลการทดลอง** ตารางเต็มอยู่ใน `EVIDENCE.md` · อ่านเอกสาร 2026-07-27

| engine | พารามิเตอร์ค้นหา HNSW | ค่าเริ่มต้น |
|---|---|---|
| **pgvector 0.8.5** | `hnsw.ef_search` | **40 คงที่** |
| Milvus | `ef` | **= limit (TopK)** |
| Weaviate | `ef` | **-1** = ปรับอัตโนมัติ 100–500 |
| OpenSearch | `ef_search` | **100** · engine `lucene` บังคับ `= k` |
| Qdrant 1.12.4 | `hnsw_ef` | ไม่ใช่ค่าคงที่ต่ำ (วัดเอง: recall@100 = 0.99 ที่ ef=40) |
| Pinecone | ไม่เปิดให้ตั้ง | — |

**`ef_search = 40` แบบคงที่ของ pgvector เป็นค่าแปลกแยกในกลุ่มนี้** —
เครื่องมืออื่นที่ตรวจได้ **ไม่ปล่อยให้ candidate list เล็กกว่าจำนวนผลที่ขอ**

→ **recall@100 = 0.3903 ไม่ใช่ธรรมชาติของ HNSW** แต่เป็นผลของการที่ pgvector
ปล่อยให้ `ef_search < LIMIT` ได้เงียบๆ (คือ Q06)

**แต่ `probes = 1` เป็นปัญหาร่วมของวงการ** — FAISS ตั้ง `nprobe = 1` ในซอร์สโค้ด
(`size_t nprobe = 1;`) และ OpenSearch ตั้ง `nprobes` เริ่มต้น 1 เหมือนกัน

## ตรวจจับล่วงหน้าได้ไหม — ได้ 11 จาก 12 ข้อ

**15 fault มีตัวฉีดและตัวตรวจครบวงจร** และตัวตรวจทุกตัว**พิสูจน์แล้วว่าพลิกสถานะได้จริง**
ไม่ใช่แค่ตอบบวกอย่างเดียว (ข้อที่ 12 คือ Q01 ซึ่ง*เป็น*การวัดเอง ไม่ใช่ข้อที่ต้องมีตัวตรวจแยก)

**คำถามที่สำคัญกว่า "กี่ข้อ" คือ "จากหลักฐานอะไร"**

| ชนิดหลักฐาน | ตรวจได้เมื่อไหร่ | fault |
|---|---|---|
| **catalog ล้วน** | เมื่อไหร่ก็ได้ · **ไม่ต้องมีข้อมูลด้วยซ้ำ** | I01 I04 I05 Q04 Q06 |
| วัดสดด้วย query เดียว | เมื่อไหร่ก็ได้หลังมีข้อมูล | I02 L02 Q03 V07 |
| **สถานะสดของ DB** | **ต้องจับตอนกำลังเกิด** | F01 F05 I03 |
| ตารางที่ตัวฉีดบันทึกไว้ | หลังตัวฉีดจบ | F03 F10 |
| ประวัติ query ที่เคยรัน | ไม่ต้องมีซอร์สโค้ด | Q02 |

**5 ข้อตรวจได้จาก catalog ล้วน** — เอาเข้า CI ได้เลย ไม่ต้องมีข้อมูล production
ไม่ต้องรัน query และไม่ต้องรอให้เกิดปัญหาก่อน

**3 ข้อต้องจับตอนกำลังเกิด** — เครื่องมือแบบสแกนครั้งเดียวจับไม่ได้เลย ระบุไว้ตรงๆ ไม่ซ่อน

### ตัวตรวจตอบ 3 อย่าง ไม่ใช่ 2

```
DETECTED / NOT_DETECTED / CANNOT_CHECK
```

**`CANNOT_CHECK` ไม่นับว่าผ่าน** — เครื่องมือที่บอกว่า "ปลอดภัย" ทั้งที่ไม่ได้ดูอะไรเลย
อันตรายกว่าไม่มีเครื่องมือ · ตัวอย่างที่ตัวตรวจ**ปฏิเสธที่จะตอบ**: I04 ปฏิเสธถ้าไม่เคยจดว่า
วัด recall บน index build ไหน — **ทีมที่ไม่เคยจดคือทีมที่เสี่ยงที่สุด ไม่ใช่ปลอดภัยที่สุด**

## หน้าผา — ความล้มเหลวเงียบไม่ค่อยมาแบบค่อยเป็นค่อยไป

สามข้อที่วัดได้ว่าเป็น **step function ไม่ใช่ทางลาด** → **ตัววัดแบบ threshold จับไม่ทัน**

| | เส้นแบ่ง | ก่อนเส้น | หลังเส้น |
|---|---|---|---|
| **Q06** | `k = ef_search + 1` | ขอ 40 ได้ 40 | ขอ 41 ได้ **40** |
| **Q03** | filter ตรง 20% → 2% | ขอ 10 ได้ 10 | ขอ 10 ได้ **0** |
| **L02** | dead tuple 40% → 50% | ขอ 10 ได้ 10 | ขอ 10 ได้ **0** |

**Q03 กับ L02 เป็นกลไกเดียวกันเป๊ะ** — index คืน candidate ตาม `ef_search`
แล้วมีอะไรมาคัดออกทีหลัง ต่างกันแค่**มองเห็นหรือไม่**

| | ตัวกรองคืออะไร | เห็นในโค้ดไหม |
|---|---|---|
| Q03 | `WHERE` ที่เขียนเอง | ✅ เห็น |
| **L02** | **MVCC** ตัดแถวที่ตายแล้ว | ❌ **ไม่มีอะไรในคำสั่งบอกเลย** |

→ L02 หายากกว่ามาก เพราะ**คำสั่งที่พังหน้าตาเหมือนคำสั่งที่ถูกทุกประการ**

## ปัญหา

ระบบข้อมูลยุคนี้เกือบทุกที่ต่อ vector search เข้าไป (RAG, ระบบแนะนำ, ค้นหาเชิงความหมาย)
แต่มันต่างจาก SQL ปกติในจุดที่อันตรายที่สุด:

| | เขียนผิดแล้วเกิดอะไร |
|---|---|
| SQL ปกติ | ได้ error หรือได้ผลผิดที่สังเกตเห็นได้ |
| **ANN search** | **ได้ผลลัพธ์ที่ดูสมเหตุสมผลเสมอ แค่ไม่ใช่ผลที่ถูก** |

ไม่มี exception ไม่มี log ไม่มี alert · dashboard เขียวหมด
ทีมงานรู้ตัวอีกทีเมื่อผู้ใช้บ่นว่า "ค้นแล้วไม่เจอ"

**นี่ไม่ใช่ข้อกล่าวหา** เอกสารทางการของ pgvector เขียนเองว่าการเพิ่ม approximate index
ทำให้ผลลัพธ์ของ query เปลี่ยนไป ไม่ใช่แค่เร็วขึ้น (ดู `EVIDENCE.md`)

QuietFail ไม่ได้ค้นพบเรื่องใหม่ — แต่**วัดว่าการแลกนั้นราคาเท่าไหร่**
ซึ่งแทบไม่มีใครวัดตอน deploy จริง

## เฉลยมาจากไหน

คำถามที่ฆ่าโปรเจคแนวนี้ส่วนใหญ่คือ **"แล้วใครบอกว่าคำตอบที่ถูกคืออะไร"**

QuietFail มีคำตอบสองชั้น:

**1. fault injection** — เราเป็นคนจงใจสร้างความล้มเหลว จึงรู้สาเหตุ 100%
ไม่ใช่การเดาจากอาการ

**2. exact search เป็นเฉลยของ recall** — การค้นแบบไม่ใช้ index
คือคำตอบที่ถูกต้องตามนิยาม ไม่ต้องมีใครมา label

วิธีบังคับ exact search เป็นวิธีที่เอกสารทางการแนะนำเอง:

```sql
BEGIN;
SET LOCAL enable_indexscan = off;
SELECT ...
COMMIT;
```

ทุกกฎที่ QuietFail ตรวจ ต้องอ้างอิงเอกสารทางการได้ — ดู `EVIDENCE.md`
ซึ่งจับคู่ fault ทุกข้อกับหลักฐาน **11 จาก 12 ข้อยืนยันจากเอกสารได้**
ส่วน **I04 เป็นข้อเดียวที่เอกสารเงียบสนิท** — ไม่มีที่ไหนรับประกันว่าสร้าง index ใหม่
แล้วได้ผลเหมือนเดิม **และไม่มีที่ไหนเตือนว่าจะไม่เหมือน** จึงพิสูจน์ด้วยการรันล้วนๆ (ทำแล้ว)

ชุด 12 ข้อล็อกไว้ที่ `FAULTS.md` ซึ่งเป็น**แหล่งอ้างอิงเดียว** · เหตุผลที่ตัด Q05/L01/V08 อยู่ที่ D15

| 1 | ใช้ docker tag `pg17` ซึ่งขยับตามเวอร์ชัน | ไม่มี error · ผลการทดลองเทียบกันไม่ได้ | ล็อกเป็น `0.8.5-pg17` |
| 2 | อ่าน GUC จาก `pg_settings` โดยไม่ `LOAD 'vector'` | ไม่มี error · คืน 0 rows · ตัวตรวจรายงานว่าผ่านทั้งที่ไม่ได้ตรวจ | บังคับ `LOAD` ก่อนเสมอ |

อันที่ 2 น่ากลัวที่สุด เพราะเป็น **false negative** — เครื่องมือตรวจสอบที่บอกว่า
"ปลอดภัย" ทั้งที่ไม่ได้ดูอะไรเลย

จึงเกิดกฎว่า **ถ้าหาสิ่งที่ควรมีไม่เจอ ต้องรายงานว่า "ตรวจไม่ได้" ไม่ใช่ "ผ่าน"**

### อันที่ 4 ต่างจากสามอันแรกตรงวิธีที่เจอ

สามอันแรกเจอเพราะ**ไปชนเข้า** — มีอาการให้เห็นก่อน ได้ error บ้าง ได้ผลว่างเปล่าบ้าง

อันที่ 4 **ไม่เคยแสดงอาการเลย** บนเครื่องที่พัฒนา เพราะเครื่องนั้นเป็น Windows
ที่ไม่มี `make` ตั้งแต่แรก มันรออยู่เฉยๆ จนกว่าจะมีคนอื่น clone ไปรันบน Linux
สิ่งที่ทำให้เจอคือการไล่ตรวจความสอดคล้องของทั้ง repo อย่างเป็นระบบ
เทียบตัวเลขในเอกสารกับค่าเริ่มต้นในโค้ดทีละจุด

**ซึ่งคือสิ่งที่ `quietfail-check` ควรทำให้ผู้ใช้พอดี** — หาความไม่สอดคล้อง
ที่ยัง**ไม่**แสดงอาการ ก่อนที่มันจะแสดง

QuietFail สาธิตคุณค่าของตัวเองกับตัวเองไปแล้วหนึ่งครั้ง
บันทึกเต็มอยู่ใน `DECISIONS.md` หัวข้อ E09

### สองอันที่หนักที่สุด — เจอทีหลัง

**E17 — ตัวสร้างข้อมูลให้ค่าเดียวซ้ำ 200,000 แถว ตั้งแต่ commit แรก**
`created_at` และ `total_satang` มีค่าไม่ซ้ำอย่างละ **1 ค่า** จาก 200,000 แถว
เพราะ `LATERAL` ที่ไม่อ้างถึงฝั่งซ้ายไม่นับเป็น correlated
planner จึงคำนวณครั้งเดียวแล้วใช้ซ้ำ · **จำนวนแถวถูก ชนิดถูก ไม่มี error**

**E19 — เครื่องมือเฝ้าระวังที่บอกว่า "ปกติดี" ตลอดกาล**
`pg_stat_activity` ถูก snapshot ครั้งเดียวต่อ transaction
ลูปเฝ้าระวังที่เขียนใน `DO` block เดียวจึงเห็นภาพเดิมซ้ำทุกรอบ
เก็บได้ 0 แถว **โดยไม่มี error ใดๆ**

อันหลังคือความล้มเหลวเงียบ **ในเครื่องมือที่สร้างมาตรวจความล้มเหลวเงียบ**

### ชื่อ fault ที่เราตั้งเอง ถูกการวัดหักล้าง 4 จาก 12 ข้อ

**ทุกครั้งจับได้ด้วยกลุ่มควบคุม ไม่ใช่ด้วยผลหลัก** — ถ้าวัดแต่สิ่งที่ตั้งใจวัด
จะยืนยันชื่อที่ผิดได้อย่างสวยงามทุกครั้ง

| ข้อ | ชื่อเดิม | สิ่งที่กลุ่มควบคุมพบ |
|---|---|---|
| **Q02** | "เขียน `WHERE` แทน `ORDER BY`" | `WHERE`+`ORDER BY`+`LIMIT` ใช้ index ได้ → **`WHERE` ไม่ใช่ตัวปัญหา** |
| **I04** | "k-means ของ IVFFlat สุ่ม" | **HNSW ไม่มี k-means เลยก็แกว่ง** · ปิด parallel ก็ยังแกว่ง |
| **I02** | "สร้าง index ตอนข้อมูลน้อย" | 50 แถวได้ **recall 1.0000** → ตัวแปรคือ**ความเป็นตัวแทน** |
| **L02** | "dead tuple → index บวม recall ตก" | `UPDATE` ทำ index บวม 195→**202 MB** แต่ **ผลครบ recall ไม่ตก** |

**กฎที่ได้:** fault ที่บอกว่า "เพราะกลไก X" ต้องหาวิธีสร้าง X **โดยไม่ให้เกิดอาการ**
เป็นกลุ่มควบคุมเสมอ · ถ้าทำได้ แปลว่า X ไม่ใช่ต้นเหตุ

## ทำไมถึงเลือกแบบนี้

เหตุผลของทุกการตัดสินใจ รวมถึง**สิ่งที่ปฏิเสธไปและเพราะอะไร** อยู่ใน `DECISIONS.md`

สรุปย่อ:

- **PostgreSQL ไม่ใช่ MySQL** — เพราะ `pg_locks`, `pg_stat_activity`,
  และ `EXPLAIN (ANALYZE, BUFFERS)` ให้ ground truth ที่โปรเจคนี้ต้องใช้
- **pgvector ไม่ใช่ Qdrant/Milvus/Pinecone** — เพราะอยู่ในฐานข้อมูลเดียวกับ harness
  ที่มีอยู่แล้ว ตรวจได้จาก catalog และปิด index หาเฉลยได้
  (**ไม่ได้เลือกเพราะเป็นตัวยอดนิยม** — ค้นแล้วไม่พบข้อมูลตลาดไทยที่ยืนยันได้)
- **ข้อมูลสังเคราะห์ในชั้น fault** — เพราะต้องคุมการกระจายตัวได้
  ถ้าคุมไม่ได้จะพิสูจน์ไม่ได้ว่า planner ประมาณผิดเพราะอะไร
- **วัดด้วย buffers ไม่ใช่เวลา** — เวลาแกว่งตามเครื่อง buffers นิ่ง

### สิ่งที่ลองแล้วไม่ได้ผล

ตั้งสมมติฐานว่า query ที่คืนแถว 12% ของตารางจะไม่ได้ประโยชน์จาก index
เพราะเกินจุดคุ้มทุนของการสุ่มอ่าน heap

**ผิด** — ผลจริงคือ PostgreSQL เลือก Index Only Scan (`Heap Fetches: 0`)
ซึ่งไม่แตะ heap เลย จุดคุ้มทุนที่ว่าจึงใช้ไม่ได้

บันทึกเต็มอยู่ใน `DECISIONS.md` หัวข้อ E07 พร้อมการทดลองต่อยอด EXP01b
ที่ออกแบบใหม่ให้บังคับอ่าน heap จริง

## เริ่มใช้งาน

ต้องมีแค่ **Docker Desktop** และ **Python 3** ไม่ต้องติดตั้ง PostgreSQL

```bash
docker compose up -d
python scripts/audit.py
```

`audit.py` ตรวจความพร้อมทั้ง repo **33 หัวข้อใน ~30 วินาที** — จำนวนแถว ·
fingerprint ของ corpus · เฉลยครบไหม · หลักฐานถูก track ครบไหม · `score.sql` ตอบได้ทุก fault ไหม

```
exit 0 = ผ่านหมด
exit 1 = มีข้อไม่ผ่าน หรือ "ตรวจไม่ได้" แล้วมันจะบอกว่าข้อไหน
```

**"ตรวจไม่ได้" ไม่นับว่าผ่าน** — docker ไม่ขึ้นก็คือตรวจไม่ได้ ไม่ใช่ปลอดภัย

### เอาไปตรวจฐานข้อมูลของคุณเอง

`sql/score.sql` เป็นตัวนับคะแนนของงานวิจัย — อ่านไฟล์เฉลยด้วย `pg_read_file()`
จึงใช้ได้เฉพาะกับ container ของ repo นี้ · **ตัวที่ยกไปใช้ที่อื่นได้คือ**

```bash
python scripts/quietfail_check.py --dsn "postgresql://user@host/db" --max-limit 100
```

ค้นหาคอลัมน์ vector และ index เอง ไม่ต้องมีไฟล์เฉลย ไม่ต้องรู้ schema ล่วงหน้า
ตรวจ **I01 · Q02 · Q04 · Q06 · I05 · V07**

| exit | ความหมาย |
|---|---|
| 0 | ตรวจครบ ไม่พบปัญหา |
| **1** | **พบปัญหา** — ควร fail build |
| **2** | ไม่พบปัญหา แต่มีข้อที่ **ตรวจไม่ได้** · ใส่ `--allow-unknown` เพื่อให้ผ่าน |

**ทำไม exit 2 ไม่ใช่ 0** — เครื่องมือที่บอกว่า "ปลอดภัย" ทั้งที่ไม่ได้ตรวจอะไรเลย
อันตรายกว่าไม่มีเครื่องมือ

มี GitHub Action ให้แล้วที่ `.github/workflows/quietfail-check.yml` —
พิมพ์ annotation ลงหน้า PR โดยตรงด้วย `--github`

**ดูคะแนนของ fault ทุกข้อ**

```bash
docker compose exec -T db psql -U lab -d faultlab -f /sql/score.sql
```

**ถ้าไม่มั่นใจว่าผลยังเกิดซ้ำได้จริง** — สั่งรันตัวฉีดจริงซ้ำได้เลย

```bash
python scripts/audit.py --reproduce          # 9 ข้อ ~40 นาที
python scripts/audit.py --reproduce Q03,L02  # เลือกเฉพาะบางข้อ
```

โหมดนี้แตะฐานข้อมูลจริง จึงตรวจ fingerprint ของ corpus ก่อน/หลัง และ index ที่ค้างให้ด้วย

ผู้ใช้ Windows ดู `WINDOWS.md` — ไม่มี `make` ต้องใช้คำสั่ง docker ตรงๆ


> ⚠️ **รหัสผ่านใน repo นี้เป็นของ container ทดลองเท่านั้น** (`labpass` · `apppass` · `obspass`)
> ตั้งไว้ให้อ่านง่ายโดยตั้งใจ เพราะทั้งชุดรันบนเครื่องตัวเองใน Docker ที่ไม่เปิดออกอินเทอร์เน็ต
> **ห้ามนำ config ชุดนี้ไปใช้กับฐานข้อมูลจริง** — โปรไฟล์ `fragile` จงใจตั้งค่าให้ระบบพังง่าย
> และตัวฉีด fault บางข้อ **ฆ่า connection ของ PostgreSQL** จึงห้ามชี้ไปที่ production เด็ดขาด
